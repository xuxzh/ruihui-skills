# 缺陷单模板与追问规则

缺陷单是禅道 `bug` 对象，会进入开发流程。本文的模板给草稿用（给用户看的是纯文本版），写库时正文转成 HTML 放进 `steps`。所有示例均为虚构数据。

## 通用结构（草稿给用户看的纯文本版）

```
即将创建的是禅道正式缺陷单（会进入开发流程），不是反馈单。

【所属产品】<产品名>（product id: <id>）
【所属项目】<项目名> / 未指定项目
【标题】<一句话概括>
【严重程度 / 优先级】<3 / 3>（默认值）
【影响版本】trunk（默认值）
【缺陷类型】<codeerror / config / ...>
【正文】
<步骤 / 实际结果 / 预期结果 / 业务场景 / 影响范围>
【查重】在你可见的 N 条缺陷中未发现重复（扫了 M 条）
```

标题写法：**现象 + 场景**，30 字以内；不写「急」「BUG」「帮我看看」这类无信息量的词，也不写「【】」标记（禅道标题里的标记会出现在列表里）。

## 正文模板（写进 `steps` 的 HTML）

```html
<p><strong>[步骤]</strong></p>
<p>1. <入口 / 页面 / 操作></p>
<p>2. <动作></p>
<p>3. <出现问题的动作></p>
<p><strong>[实际结果]</strong></p>
<p><观察到的现象；有报错就贴原文报错></p>
<p><strong>[预期结果]</strong></p>
<p><正确应该是什么样></p>
<p><strong>[业务场景]</strong></p>
<p><谁、在什么操作下遇到问题；影响谁、影响多大></p>
<p><strong>[影响范围]</strong></p>
<p><影响的功能 / 影响的人 / 是否阻断></p>
<p><strong>[环境]</strong></p>
<p><浏览器、系统、版本、账号角色等；用户没提供就写「用户未提供」></p>
```

规则：

- **段落用 `<p>`，小标题用 `<p><strong>[…]</strong></p>`**，不要用 `<h1>`–`<h6>`（禅道富文本会把标题样式带进缺陷列表）。
- **换行靠段落，不靠裸 `\n`**：禅道存的是 HTML，裸换行会被压掉（这是实测坑，见 `zentao-mcp.md`）。
- 用户没提供的段落保留该段并写「用户未提供」，不要删段——段落结构一致才好比较回读。
- 不编造版本号、模块、接口名、报错码、截图描述。

回读比较时先**剥掉 HTML 标签**，再归一化换行与连续空白，然后与上面的正文逐字比较。

## 字段默认值

| 字段 | 默认 | 什么时候改 |
| --- | --- | --- |
| `productID` | 选品结果（整数） | 只有用户明说产品时才变 |
| `title` | 草稿标题 | — |
| `openedBuild` | `["trunk"]` | 用户给了版本名 → 匹配一次版本列表；匹配不上仍用 `trunk`，并在草稿里说明 |
| `severity` | `3` | 用户明说严重程度 → 以用户说的为准 |
| `pri` | `3` | 用户明说优先级 → 以用户说的为准 |
| `type` | 按描述归类 | 归类不确定就用 `others` |
| `steps` | 上面那段 HTML | — |
| `project` | 与产品同名的项目 | 禅道的项目列表不按产品过滤（`get_projects` 传 `productID` 也返回全部可见项目）。同名项目 → 挂它；没有同名项目而只有一个 doing 项目 → 挂它；多个 doing 且无同名 → 不挂并注明「未指定项目」；用户明说 → 挂对应项目 |
| `execution` | 不填 | 不追问 |
| `module` | 不填 | MCP 没有这个参数；模块信息写进正文 |

缺陷类型（`type`）取值：`codeerror` 代码错误、`config` 配置相关、`install` 安装部署、`security` 安全相关、`performance` 性能问题、`standard` 标准规范、`automation` 测试脚本、`designdefect` 设计缺陷、`others` 其他。**只用这些值**（线上数据里出现过枚举外的值，不要跟着用）。

## 追问规则

缺陷单的追问门槛比反馈单更高：**只有缺了它缺陷就没法复现或没法验收时才追问**，其余一律用默认值。

| 缺失项 | 是否追问 |
| --- | --- |
| 现象是什么（实际结果为空） | 追问 |
| 复现步骤 | 追问 |
| 预期结果 | 追问 |
| 所属产品（用户明说、默认产品、上下文都指不出来） | 追问 |
| 业务场景、影响范围、环境 | 不追问；写「用户未提供」 |
| 严重程度、优先级、影响版本、所属项目、执行、模块、负责人 | 不追问；用默认值 |
| 用户的姓名、邮箱、工号 | 不追问；禅道里记在当前禅道账号上 |

用户答不上来时，写「用户未提供」继续走流程——草稿里留空即可，不要卡住用户。

## 追问格式

编号、选项字母、建议与理由的写法统一见 [feedback-templates.md](feedback-templates.md)「追问格式」，缺陷单直接套用。

缺陷单专属的一条：**问「要不要建成缺陷单」时**，选项固定是

```
a. 建正式缺陷单（进入开发流程）
b. 记成反馈单（不进开发流程，等评审）
```

建议怎么给，看用户表述：明确说「报错 / 复现步骤 / 崩溃」→ 建议 a；说的是不便、期望、或者他自己也不确定是不是 bug → 建议 b，并说清后果。

## 查重候选的呈现

列出候选时给全这几项：ID、标题、状态、负责人。让用户选：

```
a. 新建一条缺陷单
b. 在 <候选> 上补充
c. 都不是
```

扫描范围要如实说明（「在你可见的 N 条中未发现重复，扫了 M 条」），不说「没有重复」——禅道 MCP 没有服务端关键词检索，覆盖范围受当前账号权限与分页上限限制。扫描用查询器 `bugs --product <产品ID> --match <关键词>`（缺陷）与 `feedbacks --product <产品ID> --match <关键词>`（反馈单）。

## 补充说明模板（追加到已有正文末尾）

保留原文不动，在其后追加一段：

```html
<p><strong>──────────────</strong></p>
<p><strong>[补充说明 · 2026-03-12 · 用户口述，AI 整理]</strong></p>
<p><补充内容：复现步骤 / 业务场景 / 预期结果 / 实际结果 / 其他说明></p>
```

## 不做的事

- 不编造版本号、模块、接口名、报错码等用户没提供的事实。
- 不在正文中写「AI 建议」的结论；补充段落标注来源是事实，正文主体整理用户原意。
- 不把缺陷单写成反馈单的措辞（「建议修复」这类是反馈口吻），缺陷单写的是「什么条件下、发生了什么、与预期差在哪」。
- 不加截图占位或图片链接：正文里的图片走上传脚本（见 [workflow.md](workflow.md) 的 F5），不写占位、也不写“图片见附件”这类无法核对的描述。
