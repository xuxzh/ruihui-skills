# 错误分类与恢复

判断依据是**实际返回**，不是工具描述，也不是「保存成功」这类文案。

## 分类表

| 类别 | 特征 | 处理动作 | 对用户的说法 |
| --- | --- | --- | --- |
| 宿主侧入参校验 | 请求根本没发出：payload 缺必填字段时，真实 MCP 返回 JSON-RPC `-32602 invalid params`（HTTP 200，正文是 error，没有业务响应） | 请求没被执行，按失败处理；补齐参数后重新调用，这类重试安全 | 「参数没齐，补上后再试」 |
| 业务校验失败 | HTTP 200，正文 `{"status":"fail","message":...}` | 按 message 修正（缺业务必填项、对象不存在等），最多修正一次 | 「禅道拒绝了这次提交：<原因>」 |
| 状态机不允许 | HTTP 200，`message` 是明确的状态描述（如「状态不是已解决或已关闭的 Bug 不能激活。」） | 停止该操作，说明当前状态不允许 | 「当前状态不支持这个操作：<原因>」 |
| 认证失败（换令牌） | 脚本换令牌时报「禅道拒绝了本机凭据」（HTTP 400）或 HTTP 401 | 立即停止，请用户在自己机器上重写接入凭据（不要在对话里索要密码）；连续失败可能锁号，不反复试 | 「禅道拒绝了本机凭据，请你跑一次写入凭据的命令；连续试会被锁号」 |
| 认证失败（请求 401） | 带用户令牌的请求返回 HTTP 401 | 令牌可能已失效：重新换一个令牌重试一次；仍 401 则停止 | 「禅道令牌失效了，我换一个再试；还是不行就先停在这里」 |
| 宿主 MCP 工具身份不对 | 用宿主里直接调的禅道工具提交后，回读发现提交人是服务端固定账号 | 这类工具不能用于建单与更新；改用随包写入脚本（带当前账号的令牌） | 「刚才那条单据的提交人不是你的账号，我用带你身份的写入脚本重新提一条」 |
| 禅道账号被锁定 | 换令牌时返回「登录失败次数过多」等 | 立即停止，不再重试 | 「你的禅道账号被锁定了，去禅道解锁后我再来」 |
| MCP 未注册 | 宿主里没有禅道工具（技能自己的读写不依赖它，只影响用户直接调工具） | 可选：走 [setup.md](setup.md) 的引导安装；技能自己的读写照常走随包脚本 | 「禅道工具还没在这个 Agent 里登记（不影响我提单据）；要登记的话我现在就配」 |
| 宿主配置条目丢失 | 登记后重开宿主，`zentao` 条目不见了（被运行中的宿主回写覆盖） | 重写一次并复核；仍然不行 → 让用户按 [setup.md](setup.md)「各宿主配置」自己改宿主配置里的 `zentao` 条目（地址从 `config.local.json` 读） | 「禅道地址被宿主覆盖了，我再写一次；还不行的话，请你退出重开一下这个 Agent」 |
| 禅道账号被锁定 | 换令牌时返回「账号被锁定」「登录失败次数过多」等 | 立即停止，不再重试 | 「你的禅道账号被锁定了，去禅道解锁后我再来」 |
| 超时 / 连接中断 / 返回无法解析 | 没有结果，或结果不完整 | 走下面的「结果不确定」流程 | 「没拿到禅道的确认，我先查一下是否已经写进去了」 |
| 静默 no-op | 返回「保存成功」，但回读发现状态与 `actions` 没变 | 视为失败，如实报告；不要用流转接口重试 |
| 缺陷单字段名写错 | `post_bugs` 的 `payload` 里传了 `product` 而不是 `productID`，或 `openedBuild` 没传 | `productID` / `title` / `openedBuild` 在工具 schema 里是必填，会被参数校验拦下（JSON-RPC `-32602`，`missing properties: [...]`）——请求根本没执行，按失败处理，不重试 |
| 缺陷正文回读失配 | `steps` 回读是 HTML，裸换行与空白被规范化 | 剥标签 + 归一化空白后再比较，不要直接拿 HTML 串比 | 「禅道说成功了，但回读发现没变化，我按未成功处理」 |
| 图片上传失败 | 上传脚本报错退出（扩展名不被接受、体积超限、令牌无效、权限不足），或上传后回读字节数对不上 | 按下面的「图片上传失败」处理；上传失败**不影响**已经建好的单据 | 「这张图没能传上去：<原因>。单据已经建好，你可以在禅道里手动补图，或者把图存到本机我再试一次」 |

## 结果不确定：先查后报

创建类调用出现超时、断连、返回解析失败时，**同一份内容不重复创建**（禅道创建接口没有幂等键，重复提交会产生两条记录）。

**没有可解析的业务状态 = 结果不确定**：HTTP 200 但正文为空、或只回了 JSON-RPC error（且不是参数错误）时，禅道到底有没有写入无从得知——一律按结果不确定处理，先查后报。参数错误（`-32602`）除外：那是请求没被执行，按失败处理。

处理顺序：

1. **留基线**：写入前那次查重扫描就是基线——记下当时扫到的反馈 ID。基线之外的 ID 才可能是本次新建；基线里已有的同名反馈不是。
2. **查**：用查询器重新扫描该产品的反馈（`feedbacks --product <产品ID>`，同一次分页范围），并确认这次扫描是**完整的**：没读失败、没到页数上限、响应给了总页数。扫描不完整就按下面的「未确认」处理。
3. **判**：候选 = 基线里没有的 ID，且回读后产品、标题、完整描述（换行归一化后逐字比较）都与本次草稿一致，并且有 `opened` 流水。
   - 恰好一条 → 按已创建交付，取它的 ID 做回读校验，并说明「创建请求没拿到确认，是查询核实到的」。
   - 多条 → 报**无法唯一确认**：把候选 ID 列给用户去禅道核对，不替用户挑一条。
   - 零条 → 报**未确认**：「复查没找到本次写入的新记录，但也不能断定禅道没写进去」。让用户决定是否重新提交——第二次创建由用户发起，不自动重试。
   - 扫描不完整 → 报**未确认**，说明复查不完整、结论不成立。
4. **回读**：无论哪条路径，最终都用查询器 `feedback --id <ID>` 核对标题与描述。

「没查到」只能说明没查到，不能说成「没创建」——查询失败或扫描不完整时尤其如此。

## 补充说明：写前复核与本次流水

禅道的更新接口是**无条件覆盖**，没有版本号 CAS：别人先改过同一条反馈，你的写入会盖掉对方的内容。

1. **写前复核**：用户确认后、写入前再读一次目标反馈，核对产品、标题、原始 `desc` 是否仍与生成草稿时一致。
   - 不一致 → 停止写入，把当前原文与重新合并后的草稿交给用户确认，不自己合并后继续写。
2. **写**：只发一次更新请求。
3. **回读**：把回读的 `desc` 与**完整预期描述**归一化换行后逐字比较（不是看是否包含某几段），并确认 `actions` 里**本次新增**了 `edited`——历史上存在过 `edited` 不算证据。
4. **结果不明**：更新超时或返回无法解析时只读核实，不重放更新；核实不了就报未确认，交回用户。

## 图片上传失败

图片上传走随包脚本 `scripts/zentao-upload.mjs`，它自己会回读字节核对，失败时报错退出。**上传失败不影响已建好的单据**——单据在传图之前就建好了，报错后不要重发建单请求。

| 脚本报错 | 含义 | 处理 |
| --- | --- | --- |
| 找不到图片文件 | 路径不对，或临时文件已被清理 | 请用户重新给一次路径；不要编造路径 |
| 图片超过上限 | 超过默认 10 MiB | 请用户压缩后重试 |
| 禅道拒绝了这次上传：令牌无效 | 令牌过期或不认识这台实例 | 重跑一次脚本（脚本会自己换令牌重试）；仍失败 → 走 [setup.md](setup.md) 重新核对接入配置 |
| 禅道拒绝了这次上传：当前账号没有权限 | 该账号不能在这类单据上挂附件 | 如实说明权限边界，请用户找管理员开权限 |
| 上传失败：文件上传失败，文件格式不在规定范围内 | 扩展名不被禅道接受 | 换成 png/jpg 重试一次；仍失败 → 请用户走禅道 Web 端上传 |
| 禅道没有返回可解析的结果 | HTTP 200 但正文为空，或只回了业务失败 | 按**结果不确定**处理：先查单据上有没有多出附件，不重复上传 |
| 上传返回成功，但回读字节数对不上 | 文件没真的写进去 | 按失败处理，不把「上传成功」当真；先查禅道里的附件列表 |
| 上传返回里没有文件 ID | 禅道没给出可引用的文件标识 | 没法生成图片引用；先查禅道里有没有多出附件，别重传 |

上传失败后**不要**做的事：不要把文字描述说成「图已经放上去了」，不要改用 base64 内联绕路（禅道与消费端都不认），也不要为了带图重建一张单据。

## 写后回读：识别静默失败

每次写入后都回读并比对四样东西：

1. `product` 是否是本次写入的产品。
2. `title` 是否与提交一致。
3. `desc` 是否与**完整预期描述**归一化换行后逐字一致（不是只看包含某几段）。
4. `actions[]` 是否**本次新增**了对应动作：新建应出现 `opened`，改描述应出现 `edited`；历史上有过不算。

对不上就按失败处理，并明确告诉用户「禅道返回成功，但回读发现没有生效」。

缺陷单的比对项对应换成：`product` / `title` / `steps`（**剥掉 HTML 标签并归一化空白**后再逐字比）/ `openedBuild`（`trunk` 与「主干」是同一个值，先归一化）/ `severity` / `pri`，以及 `actions` 里的 `opened`。

## 常见 message 与含义

| message 片段 | 含义 | 处理 |
| --- | --- | --- |
| 『反馈名称』不能为空 | 参数没包在 `payload` 里，被服务端忽略 | 用 `{"payload": {...}}` 重新调用 |
| 『所属产品』不能为空 / Product does not exist. | `product` 缺失或产品 ID 不存在 | 用查询器 `products` 确认 ID 后重试一次 |
| 『评审人』不能为空 | 禅道侧业务必填项（建需求时） | 补齐或改走反馈单路径 |
| 状态不是已解决或已关闭的 Bug 不能激活。 | 状态机不允许 | 停止该操作 |
| 文件上传失败，文件格式不在规定范围内 | 禅道不接受这个扩展名（或上传没带上内容） | 换成 png/jpg 再试一次；仍失败就请用户改走禅道 Web 端上传 |

## 停止条件

出现以下情况，停止自动操作并把决定交回用户：

- 认证连续失败（重新登录后仍 401）。
- 禅道账号被锁定。
- 两次修正后业务校验仍失败。
- 写入后回读不一致且无法判定是否已落库。
- 创建结果无法唯一确认（多条候选，或复查扫描不完整）。
- 补充说明写前复核发现原文已被他人改动：把重新合并后的草稿交回用户确认。
- 用户要求的操作会关闭、删除、解决或转移单据（这些由人来做）。
- 用户要求给缺陷单指派负责人或流转状态（缺陷单也不做）。
- 用户要求的操作超出当前能力（服务端关键词搜索、反馈转 Bug；图片只能挂在反馈单与缺陷单上）。
- 用户要提交到当前账号看不见的产品或项目（权限边界，交给人开权限）。
- 登记 MCP 后重开宿主仍找不到禅道工具，重写一次仍被覆盖（交回用户走随包 connect 脚本）。

## 禁止的动作

- 不在未确认的情况下调用 `post_*` / `put_*` / `delete_*`。
- 不在结果不确定时自动重试创建或重放更新。
- 不把写入前就存在的同名反馈当成新建成功。
- 不把「没查到」说成「没创建」。
- 不把「保存成功」当成落库证据。
- 不绕过禅道权限限制去达成写入目的。
- 不在回复里输出账号、密码、token；汇报连接状态时不贴内网地址（2.7 交付反馈链接除外）。
- 不在对话里索要禅道密码或令牌，也不把它们写进任何仓库文件。
- 不用宿主 CLI 覆盖已存在的同名 MCP 条目（会丢掉该条目上的其他字段），也不改动宿主配置里 `zentao` 以外的内容。
