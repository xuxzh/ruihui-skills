# 错误分类与恢复

判断依据是**实际返回**，不是工具描述，也不是「保存成功」这类文案。

## 分类表

| 类别 | 特征 | 处理动作 | 对用户的说法 |
| --- | --- | --- | --- |
| 宿主侧入参校验 | 请求根本没发出（缺必填参数、类型不符），返回参数错误 | 补齐参数后重新调用；这类重试安全 | 「参数没齐，补上后再试」 |
| 业务校验失败 | HTTP 200，正文 `{"status":"fail","message":...}` | 按 message 修正（缺业务必填项、对象不存在等），最多修正一次 | 「禅道拒绝了这次提交：<原因>」 |
| 状态机不允许 | HTTP 200，`message` 是明确的状态描述（如「状态不是已解决或已关闭的 Bug 不能激活。」） | 停止该操作，说明当前状态不允许 | 「当前状态不支持这个操作：<原因>」 |
| 认证失败 | HTTP 401 | 重新登录一次并重试该调用一次；仍 401 则停止 | 「禅道会话已失效，重新登录后仍失败，请检查 MCP 服务的账号配置」 |
| 超时 / 连接中断 / 返回无法解析 | 没有结果，或结果不完整 | 走下面的「结果不确定」流程 | 「没拿到禅道的确认，我先查一下是否已经写进去了」 |
| 静默 no-op | 返回「保存成功」，但回读发现状态与 `actions` 没变 | 视为失败，如实报告；不要用流转接口重试 | 「禅道说成功了，但回读发现没变化，我按未成功处理」 |

## 结果不确定：先查后报

创建类调用出现超时、断连、返回解析失败时，**同一份内容不重复创建**（禅道创建接口没有幂等键，重复提交会产生两条记录）。

处理顺序：

1. **查**：用 `get_products_productID_feedbacks` 拉取该产品最近的反馈，按标题关键词匹配本次草稿的标题。
2. **判**：
   - 找到标题一致、时间接近的记录 → 认为是已创建，取它的 ID 做回读校验，按成功交付，并说明「创建请求没拿到确认，但查询到对应记录」。
   - 没找到 → 告诉用户「未确认是否已写入」，让用户决定是否再提交一次（由用户执行第二次创建，不要自动重试）。
3. **回读**：无论哪条路径，最终都用 `get_feedbacks_feedbackID` 核对标题与描述。

## 写后回读：识别静默失败

每次写入后都回读并比对三样东西：

1. `title` / `desc` 是否与提交一致（描述更新时尤其要逐段比对）。
2. `status` 是否符合预期。
3. `actions[]` 是否新增了对应动作：新建应出现 `opened`，改描述应出现 `edited`。

三者对不上就按失败处理，并明确告诉用户「禅道返回成功，但回读发现没有生效」。

## 常见 message 与含义

| message 片段 | 含义 | 处理 |
| --- | --- | --- |
| 『反馈名称』不能为空 | 参数没包在 `payload` 里，被服务端忽略 | 用 `{"payload": {...}}` 重新调用 |
| 『所属产品』不能为空 / Product does not exist. | `product` 缺失或产品 ID 不存在 | 用 `get_products` 确认 ID 后重试一次 |
| 『评审人』不能为空 | 禅道侧业务必填项（建需求时） | 补齐或改走反馈单路径 |
| 状态不是已解决或已关闭的 Bug 不能激活。 | 状态机不允许 | 停止该操作 |
| 文件上传失败，文件格式不在规定范围内 | 附件上传不可用 | 告知用户改走文字描述或禅道 Web 端 |

## 停止条件

出现以下情况，停止自动操作并把决定交回用户：

- 认证连续失败（重新登录后仍 401）。
- 两次修正后业务校验仍失败。
- 写入后回读不一致且无法判定是否已落库。
- 用户请求的操作会关闭、删除、解决或转移单据（这些由人来做）。
- 用户要求的操作超出当前 MCP 能力（附件上传、服务端关键词搜索、反馈转 Bug、区分终端用户身份）。

## 禁止的动作

- 不在未确认的情况下调用 `post_*` / `put_*` / `delete_*`。
- 不在结果不确定时自动重试创建。
- 不把「保存成功」当成落库证据。
- 不绕过禅道权限限制去达成写入目的。
- 不在回复里输出账号、密码、token 或内网地址。
