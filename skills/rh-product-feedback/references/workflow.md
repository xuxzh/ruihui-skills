示例数据均为虚构。流程主干见 `SKILL.md`，本文给出逐步细节与输出样例。

## F0 首次接入（连接禅道）

用户第一次用，或宿主里还没有禅道工具时。**地址不回显，凭据不由 agent 写**。

**技能没装**（宿主里找不到这个技能）：让用户把安装提示词发给你——提示词见 [setup.md](setup.md)「安装提示词」，它让当前宿主自己装技能、自己装官方禅道 CLI、自己写接入凭据。

**技能装了但禅道工具不可用**（宿主里没有 `zentao` 工具）：按 [setup.md](setup.md)「Agent 执行路径」的五步走——装官方禅道 CLI、由终端用户本人写凭据、只读自检；**不登记禅道 MCP**。

自检用入口脚本 `products`（脚本自己换当前账号的令牌），然后**如实说明两件事**：

- 凭据已写入本机，本次操作用的是它换出来的、属于终端用户账号的令牌；
- 单据会留痕在终端用户自己名下——回读到的提交人应当就是他本人；不是本人就如实说明（见 `setup.md` 的「禅道 MCP：只给人手动查看」）。

用户说「好了」或直接说业务诉求，都不再多问。自检通过时不插入额外的「自检报告 → 等确认」往返。

自检仍连不上时，按 [setup.md](setup.md)「连不上时怎么查」逐项核对：地址取自技能包的 `config.local.json`，凭据由用户本人在本机重写；**不要去改宿主配置**。仍不行 → 让用户去禅道 Web 端提交。

## F1 提交反馈

### 1. 收要素

按 `feedback-templates.md` 判定类型与必填项，一次问全缺失项；呈现格式按同文件的「追问格式」。

对话样例：

> ❓ **Q1** - **这是在哪个页面/入口操作时出现的？**（写不出入口，开发没法复现）
>
> a. 设备管理列表页
> b. 设备管理列表页 → 导出按钮
> c. 设备详情页
> d. 其他（写下页面名）
>
> ➡️ **建议 b**：设备管理列表页的导出按钮。
> 理由：你刚才说的就是导报表没反应，入口越具体开发越能直接定位。
>
> 回复：回一个字母（b）；也可以说「按建议」，我就按 b 继续。
>
> ---
>
> ❓ **Q2** - **期望的正确结果是什么？**（验收标准）
>
> ➡️ **建议**：导出 Excel 文件；导不出时给一条明确的失败原因（哪个字段不合法、哪条数据有问题）。
> 理由：这两条都能判定通过或失败；「别再没反应」判不了。
>
> 回复：回一句就行；也可以说「按建议」。

### 2. 草稿

草稿要展示到用户能逐字判断的程度：

```
类型：Bug
所属产品：示例产品 A（product id: 101）
标题：设备列表导出按钮点击后无响应

描述：
【业务场景】
运维人员在设备管理页导出月度报表。

【复现步骤】
1. 打开「设备管理」
2. 选择时间范围后点「导出」
3. 页面无任何变化，控制台无报错

【实际结果】
点击后无响应，也无失败提示。

【预期结果】
应导出 Excel 文件，或给出明确的失败原因。

【影响范围】
阻断月度报表导出。

【环境】
用户未提供
```

### 3. 查重

入口脚本 `node <技能目录>/scripts/zentao.mjs dup --kind feedback --product <产品ID> --title "<用户的标题>"`：脚本把标题切成**中文二元组**（英文按词），生成「组内且、组间或」的关键词变体组交给禅道 CLI 在客户端匹配，只在标题里找——**正文里出现的词不算命中**。词序不同也算重复：用户说「切换语言功能失效」，禅道里写的「语言切换功能失效」会被命中。

脚本给三样东西：候选表格（编号、标题、状态、负责人、匹配度）、覆盖范围（`# 覆盖范围：…`）、查重基线（最后一行 JSON 的 `baseline`，是本次扫描到的全部单据 ID，JSON 里的 `complete` 说明这次扫描扫全了没有）。

覆盖范围有两种说法，别混：

- 扫全了：`# 覆盖范围：在你可见的 42 条反馈中发现 1 条相近记录（在标题里命中 1 条）`
- 没扫全（服务端分页不前进，只读到第 1 页）：`# 覆盖范围：只扫到 20 条反馈，服务端称共有 51 条，服务端分页未向前推进，覆盖不完整——这 20 条里未发现重复，不等于全部可见记录里没有`。这种时候**必须跟着说出来**：这次只扫到 20 条、覆盖不完整，不能说成「没有重复」，也不能拿这个基线判定「新建之外没有别的」。

输出样例：

> 在你可见的 42 条反馈中发现 1 条相近记录：
> - #318「设备列表导出无响应」— 状态 wait — 负责人 张工
>
> ❓ **Q3** - **这条反馈是新建还是复用？**（禅道里最终是 1 条还是 2 条）
>
> a. 新建一条
> b. 在 #318 上补充说明
> c. 都不是
>
> ➡️ **建议 b**：在 #318 上补充说明。
> 理由：#318 记的就是同一个现象，禅道里留两条会让评审各看一半、容易漏掉；你这条要是还带了它没写过的信息（报错原文、发生时段），在补充里一并写上就行。
>
> 回复：回一个字母（b）；也可以说「按建议」，我就按 b 继续。

措辞边界：说「在你可见的 42 条中未发现重复」，不说「禅道里没有重复」——可见范围由当前账号的禅道权限决定；没扫全时连这句也不说，直接说「只扫到 20 条、覆盖不完整」。

取舍：标题很长时（两两配对会超过 40 组），脚本改用相邻窗口（相邻二元组 + 长度为 3 的滑动窗口）匹配，组数不再平方增长；代价是共有的词在标题里隔得远时可能匹配不到，这时把 `--title` 换成最有区分度的几个字再扫一次。

### 4. 确认

用户回复「新建」即可视为对当前草稿的明确确认。回复只有「嗯」且尚未展示草稿时，先展示草稿再问一次。

### 5. 创建

先把载荷写进临时文件，再交入口脚本；**正文只走文件，不进命令行参数**。

```json
{"product": 101, "title": "设备列表导出按钮点击后无响应", "type": "bug", "desc": "<草稿描述全文>"}
```

```bash
node <技能目录>/scripts/zentao.mjs feedback-create --payload-file /tmp/rh-zentao-payload.json
```

- `product` 写**整数**（字符串形态会被服务端静默忽略）；`desc` 是**纯文本**描述，不写 HTML 标签；`source` / `module` 不填。
- 反馈者 `feedbackBy` **不用你填**：入口脚本按当前禅道账号显式补上——这台实例的禅道不自动记录反馈者，不显式写就永远没有反馈者。载荷里填了别的账号会被拒绝。
- **只发一次**：脚本只发一次创建请求，禅道创建没有幂等键，不要自己再补一次。临时文件由脚本用完即删。
- 反馈单**不附带建缺陷单**：禅道没有「反馈转缺陷」的关联字段，一次诉求只建一张单。
- 脚本写入前先拍一次查重基线（该产品下的反馈编号）。**基线不完整**（服务端分页不前进，只扫到第 1 页）时，它不能用来判断「哪条是本次新建」：这时写入结果不确定只能报未确认，不能判成功，也不重发（输出里 `baselineComplete:false`、`uncertain:true`）。

### 6. 回读

`feedback-create` 已经按返回的编号做过回读核对：`product` / `title` / 完整 `desc`（纯文本，只归一化换行与行尾空白）/ 反馈者 / **创建者字段 `openedBy`** / `actions` 里**本次新增**的 `opened`（历史上存在过不算）；CLI 0.4.4 不返回 `actions` 时，改用 `openedBy` + `openedDate` 核对。它把结论、交付要素与核对依据打成一行 JSON：

```
{"ok":true,"kind":"feedback","id":421,"title":"设备列表导出按钮点击后无响应","status":"active","product":101,"type":"bug","feedbackBy":"zhangsan","openedBy":"zhangsan","submitterField":"openedBy","submitterIsCurrentAccount":true,"url":"<禅道 Web 地址>/feedback-view-421.html","verified":"readback"}
```

- **提交人核对看的是创建者字段 `openedBy`**：这台实例的禅道不自动记录反馈者（`feedbackBy` 可能恒为空），拿它核对会得出「提交人是别人」的错结论。回读里取不到 `openedBy`（字段名与本实例不一致）时，`mismatches` 里会出现「创建者字段（openedBy）」——**如实报告，不要猜哪个字段是提交人**。
- `verified: "readback"` → 回读通过。`verified: "query"` → 创建回执丢了（超时 / 断连），结论来自重查该产品后唯一一致的新记录，**交付时要说明「编号来自查询核实」**。
- `ok:false` + `created:true` + `mismatches` → 单据建出来了但内容对不上：**不要重建**，把不一致项与单据现状告诉终端用户。
- `ok:false` + `uncertain:true` → 是否建成**未确认**：不重发，把 `candidates` 列给终端用户并请他自己在禅道里看一眼；**不要把「没查到」说成「没创建」**。
- 终端用户要细节时，再用入口脚本 `feedback --id <ID>` 读一遍正文、流水与历史。

回读不到或内容不一致 → 见 `error-handling.md`，不要重新创建。

创建请求超时、断连时也一样：重查该产品的反馈，只认「基线之外、唯一、回读完全一致」的那条。

```
✓ 创建请求没拿到确认，但查询核实到已创建：反馈 #421（已回读一致）

⚠ 未确认是否已写入：复查没找到本次写入的新记录，也没有重复创建。请到禅道核对后再决定要不要重新提交。

⚠ 无法唯一确认：查到 2 条可能本次创建的记录（#421、#423），请到禅道核对哪条是你的。我没有重复创建。
  链接：<禅道 Web 地址>/feedback-view-421.html
  链接：<禅道 Web 地址>/feedback-view-423.html
```

### 7. 交付

```
已提交反馈 #421（示例产品 A）
- 标题：设备列表导出按钮点击后无响应
- 类型：Bug
- 当前状态：wait（待评审），未指派负责人
- 反馈者：zhangsan（禅道里 `feedbackBy` 记的就是你本人）
- 提交人：zhangsan（回读到的 `openedBy`，创建者字段，就是你自己）
- 链接：<禅道 Web 地址>/feedback-view-421.html（读不到 `zentaoWebUrl` 就不给这一行，只给编号）
下一步：等评审结果；要补充信息随时说「补充反馈 #421 ...」
```

- **反馈者与创建者都是本人** → 说「这条反馈单的反馈者与提交人都是你」。
- **两者不一致**（如反馈者字段记的是 `zhangsan`、创建者是 `lisi`）→ 如实说「反馈者字段记录的是 zhangsan，创建者（留痕主体）是 lisi」，**不粉饰**。
- `submitterIsCurrentAccount` 为 `false` → 禅道里这条单据的提交人是别人，如实说明（见 `setup.md` 的「禅道 MCP：只给人手动查看」），不要把服务端的提交人当成终端用户本人。
- `url` 为 null（技能包没配 `zentaoWebUrl`）就不给链接，只给编号并说明原因。

## F1b 提交缺陷单

缺陷单会进开发流程，所以草稿与确认比反馈单更明确。

### 1. 收要素

按 `bug-templates.md` 判定必填项。**禅道字段不追问**（严重程度、优先级、版本、执行、模块走默认值）。

选品优先级：用户这次明说的产品 > 本机默认产品 > 追问一次。只有明说与默认都没有时才问：

> ❓ **Q1** - **这条缺陷记到哪个产品下？**（禅道按产品分派开发）
>
> a. MOMV2.0（示例产品 A）
> b. 瑞辉智能报表平台（示例产品 B）
>
> ➡️ **建议 a**：你前面说的就是这个系统的功能。
> 理由：产品错了单子会落到别的团队名下，白等一轮。
>
> 回复：回一个字母（a）；也可以说「按建议」，我就按 a 继续。

### 2. 草稿

纯文本版给用户看，末尾带声明：

```
即将创建的是禅道正式缺陷单（会进入开发流程），不是反馈单。

所属产品：MOMV2.0（product id: 1）
所属项目：MOMV2.0-RD

严重程度 / 优先级：3 / 3（默认值）
影响版本：trunk（默认值）
缺陷类型：codeerror
负责人：未指派（随包默认不指派；生效值是产品 QD 时用 `qd --product 1` 查出账号与姓名，写「产品 QD：<账号>（<姓名>）」；该产品没有 QD 写「未指派（该产品没有 QD）」；用户指名就写他的账号）

【步骤】

点击后无响应，控制台报 500。

应导出 Excel 文件，或给出明确的失败原因。

【业务场景】
仓管每天下班前导出对账。

【影响范围】
阻断月度报表导出。

【环境】
用户未提供
```

> 在你可见的 300 条缺陷中发现 1 条相近记录：

>

### 4. 确认

用户回复「新建」即可视为对当前草稿的明确确认。草稿里必须带「即将创建的是禅道正式缺陷单（会进入开发流程）」这一行。

只回「嗯」「行吧」而没看到草稿 → **先把草稿贴出来再问一次**；草稿改过（换了产品、加了正文、改了负责人）→ 重新贴新草稿再确认。没拿到明确确认，不调写入命令。

### 5. 创建

先把载荷写进临时文件，再交入口脚本；**正文只走文件，不进命令行参数**。

```json
{"productID": 1, "title": "设备列表导出按钮点击后无响应", "openedBuild": ["trunk"], "severity": 3, "pri": 3, "type": "codeerror", "steps": "<正文 HTML>"}
```

```bash
node <技能目录>/scripts/zentao.mjs bug-create --payload-file /tmp/rh-zentao-payload.json
```

- 字段名是 `productID`（反馈单是 `product`），`openedBuild` 是字符串数组，`severity` / `pri` 写数字（CLI 不接受字符串）。文件里放请求体本身，不要再套一层 `payload`。
- **只发一次**：脚本只发一次创建请求，禅道创建没有幂等键，不要自己再补一次。临时文件由脚本用完即删。
- 负责人不写在这个载荷里：入口脚本按「默认负责人」配置补——随包默认 `""` 补空串（不指派，挡住禅道侧默认指派），代码兜底 `"qd"` 不带这个字段（由禅道按产品的 QD 指派），用户明确指名才写他的账号。见 [setup.md](setup.md)「默认负责人」。
- 脚本写入前先拍一次查重基线（该产品下的缺陷编号），结果不确定时只用它判断哪些编号是本次新建的。**基线不完整**（服务端分页不前进，只扫到第 1 页）时这个判断不成立：结果不确定只能报未确认（输出里 `baselineComplete:false`、`uncertain:true`），不判成功、不重发。

### 6. 回读

`bug-create` 已经按返回的编号做过回读核对：`product` / `title` / `steps`（**剥标签 + 归一化空白**后逐字比较；图片引用按 `fileID` 归一，服务端补的属性不算内容差异）/ `openedBuild`（`trunk` 与「主干」归一化）/ `severity` / `pri` / `assignedTo`，以及 `actions` 里**本次新增**的 `opened`（历史上存在过不算）；CLI 0.4.4 不返回 `actions` 时，改用 `openedBy` + `openedDate` 核对。它把结论、交付要素与核对依据打成一行 JSON：

```
{"ok":true,"kind":"bug","id":1935,"title":"设备列表导出按钮点击后无响应","status":"active","assignedTo":"","assigneeSource":"package","openedBy":"zhangsan","url":"<禅道 Web 地址>/bug-view-1935.html","verified":"readback"}
```

- `verified: "readback"` → 回读通过。`verified: "query"` → 创建回执丢了（超时 / 断连），结论来自重查该产品后唯一一致的新记录，**交付时要说明「编号来自查询核实」**。
- `ok:false` + `created:true` + `mismatches` → 单据建出来了但内容对不上：**不要重建**，把不一致项与单据现状告诉终端用户（该改的自己改不了：技能不流转、不改单据）。
- `ok:false` + `uncertain:true` → 是否建成**未确认**：不重发，把 `candidates` 列给终端用户并请他自己在禅道里看一眼；**不要把「没查到」说成「没创建」**。
- 终端用户要细节时，再用入口脚本 `bug --id <ID>` 读一遍正文、流水与历史。

负责人的生效值：`assigneeSource` 为 `qd` 时由禅道按产品 QD 指派——草稿里写的 QD 是用 `qd --product <产品ID>` 查出来的「谁来承接」，回读到的 `assignedTo` 才是生效结果；两者对不上（例如 QD 账号已锁定）就如实说明，不要改单据。为 `package` / `local` / `user` 时断言 `assignedTo` 与载荷一致（`""` 就是未指派）。

### 7. 交付

```
已提交缺陷单 #1935（MOMV2.0）
- 标题：设备列表导出按钮点击后无响应
- 所属项目：MOMV2.0-RD
- 严重程度/优先级：3 / 3
- 影响版本：trunk
- 当前状态：active
- 负责人：未指派（随包默认未指派）
- 提交人：zhangsan（回读到的 openedBy，就是你自己）
- 链接：<禅道 Web 地址>/bug-view-1935.html
下一步：等开发认领；要补充信息随时说「补充缺陷 #1935 ...」
```

负责人一栏按 `assigneeSource` 说清来源：`user` 终端用户指名 / `local` 本机默认 / `package` 随包默认未指派 / `qd` 产品 QD。`openedBy` 与当前禅道账号不一致时如实说明「禅道里这条单据的提交人是 <另一个人>」。`url` 为 null（技能包没配 `zentaoWebUrl`）就不给链接，只给编号并说明原因。

### 默认负责人

用户说「以后提 bug 默认不指派」「默认都指给张三」时，把值合并写进偏好文件的 `bugAssignee`（别覆盖文件里已有的 `defaultProduct`），回读复核后告知用户。取值含义与生效顺序见 [setup.md](setup.md)「默认负责人」。

随包默认是不指派（`bugAssignee` 为 `""`）；配成 `"qd"` 时才由产品 QD 承接——交给谁先用 `node <技能目录>/scripts/zentao.mjs qd --product <产品ID>` 查（账号、姓名、账号状态、最后登录），承接结果以回读到的 `assignedTo` 为准。

### 默认产品

用户说「默认产品是 <产品名>」时：

1. 入口脚本 `products` 拿一遍可见产品（脚本输出当前账号能看到的全部产品，需要时按名称自己比对）确认它在当前账号可见范围内；不可见就如实说明并让用户换一个。
2. 把要写的内容给用户确认（产品 id + 名称）。
3. 写入用户机器上的偏好文件 `~/.config/rh-zentao/preferences.json`：

   ```json
   { "defaultProduct": { "id": 1, "name": "MOMV2.0" } }
   ```

4. 回读复核文件内容，再告诉用户「默认产品已设为 <名称>」。

**绝不写进技能包的 `config.local.json`**——那会随技能包分发给所有用户，把一个人的产品变成别人的默认值。

使用时的规则：默认产品只是默认值，用户这次说了别的产品就用用户说的；默认产品当前不可见就如实说明并列出可见产品，不静默换产品建单。

## F2 查询单据

### 定位

- 给了编号 → 看上下文判断单据类型：缺陷 `node <技能目录>/scripts/zentao.mjs bug --id <ID>`，反馈 `feedback --id <ID>`。
- 给了产品或标题 → 先列单据，再让他挑编号打开：

```bash
node <技能目录>/scripts/zentao.mjs bugs --product 29 --match 切换语言   # 缺陷单
node <技能目录>/scripts/zentao.mjs feedbacks --product 29 --status wait  # 反馈单
```

列表是「一次拉全量 + 字段投影 + 客户端筛选」：脚本用 `--all` 把所有页取完、只留投影字段、在进程内按 `--status` / `--match` 过滤，所以表头的「可见 N 条」是当前账号在这个产品下能看到的**全部**，不是第一页；`--match` 只匹配标题，正文里的词不算命中。

### 输出格式

列表（表格，十几行；默认 10 条）：

```
# 缺陷（产品 29 可见 12 条，已扫 12 条，筛选后 2 条）
1945	切换语言后页面文案仍是中文	resolved	dev-a	2/2
1946	语言切换不生效	closed	dev-b	3/2
```

表头把**扫了多少条、扫全没有**说在前面：扫全了是「可见 N 条，已扫 N 条」；服务端分页不前进时是下面这样——第 1 页的记录照常列，但明说覆盖不完整，**不许把第 1 页当成全部**：

```
# 反馈（产品 29 扫到 20 条，服务端称共有 51 条，服务端分页未向前推进，覆盖不完整，只列前 10 条）
# 反馈（产品 29 扫到 0 条，服务端分页未向前推进，覆盖不完整）
```

还有一种情况：服务端回的记录 `product` 字段不是请求的产品（实测请求产品 29 的反馈列表，回的是产品 1 的记录）。这类记录**已丢弃**，表头里会点名——不能拿别的产品的数据当这个产品的：

```
# 反馈（产品 29 扫到 0 条，禅道返回的 20 条记录 product 字段是 1，不属于产品 29，已丢弃）
```

这两种表头都要照实转述：哪些是本产品的、哪些被丢了、覆盖全不全。不要自己“补全”成「可见 N 条」或「未发现重复」。

详情（一行 JSON，节选）：

```json
{"ok":true,"kind":"bug","id":1945,"product":29,"title":"切换语言后页面文案仍是中文","status":"resolved","assignee":"dev-a","openedBy":"zhangsan","openedDate":"2026-03-10 09:00:00","processor":"dev-a","processedDate":"2026-03-12 15:30:00","resolution":"fixed","body":"[步骤] 打开设置 → 切换语言\n[结果] 文案没变","actions":[{"id":19451,"action":"opened","actor":"zhangsan","date":"2026-03-10 09:00:00","comment":"（空）","changes":[]},{"id":19452,"action":"resolved","actor":"dev-a","date":"2026-03-12 15:30:00","comment":"（空）","changes":[{"field":"status","from":"active","to":"resolved"}]}]}
```

讲给用户时把 JSON 里的事实转成人能读的几行，样例：

```
缺陷 #1945（示例产品 A）
- 标题：切换语言后页面文案仍是中文
- 当前状态：resolved（已解决），结论 resolution = fixed（已修复）
- 负责人：dev-a；处理人：dev-a，处理时间：2026-03-12 15:30
- 提交人：zhangsan，2026-03-10 09:00 提交
- 处理时间线：
  · 2026-03-12 15:30 dev-a resolved（status：active → resolved）
  · 2026-03-10 09:00 zhangsan opened
```

## F3 解释处理进度

三段式，段落之间明确分开：

```
事实
- status = resolved，resolution = fixed（都是禅道字段原值）
- 负责人 assignedTo = dev-a
- 处理人 resolvedBy = dev-a，处理时间 resolvedDate = 2026-03-12 15:30
- 流水 2 条：2026-03-10 09:00 zhangsan opened；2026-03-12 15:30 dev-a resolved 并把 status 从 active 改成 resolved
- plan 与 version 字段为空

推断（每条都标注是推断）
- 推断：这条已经改完、在等验证（依据：resolution = fixed，且之后没有新的流水）
- 推断：下个版本能带上（依据：状态已到 resolved，但禅道里没有版本字段，这条推断可信度低）

无法确定
- 禅道里没有排期记录，也没有评论说明何时上线
- 验证人是谁、什么时候验：禅道里没有这个字段
```

关键纪律：**没有排期 ≠ 被拒绝**。前者是事实，后者只能是推断，且必须写明是推断。事实段落里也不要解释字段含义之外的因果（「因为负责人忙」不是事实）；流水里带 `"new": true` 的是本次写入新增的动作，其余是历史动作，两边不要混着讲。

反馈单走同一套三段式，只是字段名不同：处理人/处理时间取 `processor` / `processedDate`（禅道字段 `processedBy` / `processedDate`），结论取 `resolution`（禅道字段 `solution`），另有 `reviewer` / `reviewedDate`（评审人、评审时间）——评审已发生但 `resolution` 为空时，只能说「禅道里还没有结论」，不能替他下结论。

## F4 补充说明

禅道没有「只评论不改状态」的接口：关闭、激活、解决都会改单据状态，所以补充说明只能**改正文**（反馈单改 `desc`，缺陷单改 `steps`，追加 HTML 段落），其余步骤一样。整条路径一步不缺：读原文 → 生成追加草稿 → 用户确认 → 写前复核 → 更新 → 回读。

### 1. 读原文

```bash
node <技能目录>/scripts/zentao.mjs feedback --id 421   # 输出里的 body 就是当前原文
node <技能目录>/scripts/zentao.mjs bug --id 1936
```

### 2. 追加草稿

原文完整保留，下面加一行分隔行，再加标注与追加段落：

```
<原有 desc 全文>

──────────────
【补充说明 · 2026-03-12 · 用户口述，AI 整理】
【复现步骤补充】
补充：必须先选中至少一行设备，点「导出」才复现；不选直接点没反应。
【预期结果补充】
导出 Excel，文件名格式 yyyyMM设备清单.xlsx
```

分隔行固定是一行 14 个 `─`，标注行以「【补充说明 · 日期 · 用户口述，AI 整理】」开头。脚本按分隔行把草稿拆成「原文」与「追加段落」两部分，所以草稿里必须有这一行。缺陷单的追加段落（含标注行）写成 HTML 段落（`<p>…</p>`），给用户看时用纯文本版。

### 3. 用户确认

把完整的新正文（原文 + 分隔行 + 标注 + 追加段落）给终端用户看，等他明确确认；没看到草稿就点头的，不算确认。

### 4. 写前复核

载荷里带上 `expectedBody`（用户确认时看到的那份原文）。脚本在写入前会再读一次这条单据，把当前正文、标题、产品与它比对；对不上就**停手**，一个更新请求都不发，把当前原文与重新合并后的草稿交回用户：

```
⚠ 这条反馈在你确认期间被改过，我还没写入。下面是它现在的原文和我重新合并后的草稿，确认后我再更新：
<当前原文>
<重新合并后的完整描述>
```

脚本输出是一行 JSON：`{"ok":false,"kind":"feedback","id":421,"conflict":true,"changed":["正文"],"currentBody":"…","currentBodyText":"…","mergedDraft":"…","mergedDraftText":"…"}`，退出码非 0。把 `currentBodyText` 与 `mergedDraftText` 念给用户，等他重新确认后再走一遍——这次 `expectedBody` 用当前原文。

### 5. 更新

```bash
node <技能目录>/scripts/zentao.mjs feedback-update --id 421 --payload-file /tmp/rh-payload.json
node <技能目录>/scripts/zentao.mjs bug-update --id 1936 --payload-file /tmp/rh-payload.json
```

载荷文件里放请求体本身，不要再套一层 `payload`：

```json
{"product": 101, "title": "设备列表导出按钮点击后无响应", "desc": "<原文 + 分隔行 + 标注 + 追加段落>", "expectedBody": "<用户确认时看到的那份原文>"}
{"title": "设备列表导出按钮点击后无响应", "steps": "<原文 + 分隔行 + 标注 + 追加段落>", "expectedBody": "<用户确认时看到的那份原文>"}
```

`product` 与 `title` 沿用当前值（禅道要求这两个字段；脚本也会按当前值补齐）。只发一次更新请求；正文只走文件，不进命令行参数。

写进去的正文 = 禅道里那份当前原文（**原样保留**，不重排版）+ 追加段落；草稿里的原文部分只用来核对，不会覆盖服务端那份。

- `expectedBody` 必填：写前复核靠它核对原文，缺了脚本报错、一个请求都不发。
- 反馈单的 `product` 写数字（字符串禅道会静默忽略）；缺陷单的更新**不能**带 `productID`（禅道 CLI 会报 E2009）。
- **不要**传空字符串去清字段：禅道 CLI 的更新动作默认 autoFill，会用当前值补齐没显式传的字段。

### 6. 回读

脚本写完自己按编号回读：把正文与**完整预期正文**归一化后逐字比较（缺陷单先剥标签，图片引用按 `fileID` 归一），有 `actions` 时确认这次**新增**了 `edited`（历史上有过 `edited` 不算）；CLI 0.4.4 不返回 `actions`，这时以正文逐字一致为准。

```
已更新反馈 #421（追加 1 段说明）
- 原文保留，描述从 320 字增加到 512 字
- 操作流水新增：edited（当前禅道账号）
```

输出是一行 JSON：`{"ok":true,"kind":"feedback","id":421,"title":"…","status":"active","updated":true,"verified":"readback","newActions":["edited"]}`。

更新超时或返回无法解析时只读核实（脚本会再读一次），不重放更新；核实不了就说「未确认是否已更新」，把现状交回用户。

禅道更新接口无条件覆盖、没有版本号 CAS：写前复核能显著降低覆盖别人内容的风险，但复核与写入之间仍可能有别人改过——发现原文变了就停手。

## F5 正文带图片

用户给了截图（或在对话里粘贴了图片）时，建单之后多两步：**传图 → 更新正文**，最后**回读**。顺序不能颠倒——禅道的上传要带单据类型与单据 ID，图片只能挂在已经存在的单据上，所以一定是先建单。

### 1. 拿到图片

宿主把粘贴的图片存成本机文件，并把路径贴进消息（pi 粘贴图片会写进临时目录并把路径贴出来）。先 `read` 这个图片文件，确认它对应正文里的哪一段描述。

### 2. 图片拿不到时

```
你发的这张图我这边拿不到文件（只有截图，没有能读到的路径）。两个办法：
- 把图片存到本机，把路径发我，我传上去；
- 我先按文字把单据建好，你到禅道里手动补图。
```

不要编造路径，也不要把「用户描述了图里有什么」当成图片已经放上去。

### 3. 传图

```bash
node <技能目录>/scripts/zentao.mjs file-create --file <图片路径> --object-type feedback --object-id <反馈 ID>
```

缺陷单把 `--object-type` 换成 `bug`。图片路径**相对命令执行目录**解析：给相对路径就按调用脚本时所在的目录找图，给绝对路径照用。脚本不产生临时文件，也不删用户给的图片。

输出是一行 JSON：

```json
{"ok":true,"kind":"file","fileId":6530,"objectType":"feedback","objectId":421,"extension":"png","reference":"<img src=\"/index.php?m=file&f=read&t=png&fileID=6530\" alt=\"file-read-6530.png\" />"}
```

`fileId` 是禅道里的附件标识，`objectType`/`objectId` 是这次上传请求带的挂载对象——**它就是目标单据**（禅道 CLI 没有 `file get` / `file list`，附件的身份只能靠上传返回的标识与挂载对象核对）。`reference` 是要放进正文的那一行引用。

### 4. 更新正文

把图片引用放进**追加段落**里，再按 F4 的可靠路径走（草稿 → 用户确认 → 写前复核 → 更新 → 回读）。反馈单改 `desc`，缺陷单改 `steps`。

为什么必须放追加段落：更新的草稿是「原文 + 分隔行 + 追加段落」，脚本要求草稿的**原文部分**与 `expectedBody`（用户确认时看到的那份原文）逐字一致，追加段落写在分隔行之后。试图把图片插进正文中间会与 `expectedBody` 对不上，脚本报冲突并不写入。

**图片落在单据正文里**（这是终端用户要的效果），位置是**原文之后的追加段落**——不是插在正文中间，也不是只挂在附件列表里。段落的标签按场景写（「截图 1」之类），由载荷的 `appendLabel` 指定，脚本在分隔行后补一行「【截图 1】」；不写 `appendLabel` 就沿用草稿里自己写的标签（补充说明流程写「【补充说明 · 日期 · 用户口述，AI 整理】」）。

草稿给用户看时用纯文本版，图片位置写「【截图 1】」，引用行附在下面：

```
即将更新的正文（反馈 #421）：
【业务场景】
仓管每天下班前导出对账。
【复现步骤】
1. 打开设备列表页
2. 点「导出」
3. 页面无响应

────
【截图 1】
<img src="/index.php?m=file&f=read&t=png&fileID=6530" alt="file-read-6530.png" />
```

载荷里的 `desc`（缺陷单是 `steps`）写「完整原文 + 空行 + 分隔行 + 图片引用」，`expectedBody` 写用户确认时看到的那份原文，`appendLabel` 写「截图 1」。缺陷单的追加部分按纯文本逐行写（分隔行、标注行、引用行，不包 `<p>`）——F4 的 `<p>` 规则说的是手写的补充说明段落。

### 5. 回读与交付

回读分两件：

- **正文写进去了**：更新命令自己回读，完整预期正文归一化后逐字一致才算成功；有 `actions` 时再确认本次新增了 `edited`（CLI 0.4.4 不返回 `actions`，不拿它判失败）。
- **引用指向的就是这次上传的附件**：正文里那行引用的 `fileID` 与传图返回的 `fileId` 一致；附件挂载对象是传图输出里的 `objectType`/`objectId`（目标单据）——这两个值是**上传请求带的**，服务端不回读挂载对象（CLI 没有 `file get` / `file list`），所以「挂在哪张单据上」靠上传请求与正文里的引用两头对上。

注意：查询输出（`bug --id` / `feedback --id`）会把 HTML 标签剥掉，**图片引用**保留成 `<img fileID="6530">`（只认文件标识，服务端补的 `onload` 等属性不显示）—— 看得到「正文里指着哪张图」，要看图本身就得打开禅道单据。

交付时说明正文里带了几张图：

```
已建反馈 #421（瑞辉智能报表平台）
- 标题：导出按钮点击后无响应
- 正文：含 1 张截图（文件 #6530）
- 状态：待评审
```

### 6. 引用标签的形态

正文里的图片引用固定长这样：

```html
<img src="/index.php?m=file&f=read&t=<扩展名>&fileID=<文件 ID>" alt="file-read-<文件 ID>.<扩展名>" />
```

- 用**相对路径**，不要写绝对地址（禅道地址随部署变，写死会在别的环境失效）。
- `t` 是扩展名（小写、不带点），`fileID` 是上传返回的文件 ID。
- 不要用 base64 内联（`data:` 开头的 src）：禅道与消费端都不认这种写法。

### 7. 边界

- 一次诉求挂几张图就传几张，各自带一个标签；不要把多张图拼成一张。
- 上传失败按 [error-handling.md](error-handling.md) 的「图片上传失败」处理：单据已经建好，如实说图没传上去，不重建单据，也不改用文字描述假装图已经放上去。
- 上传结果不确定（超时、读不懂响应）：图片可能已经挂上去了——先去单据里看有没有多出这个附件，**不重复上传**（上传没有幂等键，重复会多出附件）；查不到就报未确认。
- 删除单据时图片是否一并清理由禅道决定，技能不承诺。

## 身份与权限的措辞

当前会话是**终端用户自己的禅道账号**在操作：随包脚本用他的凭据换一个属于他的令牌，带着令牌访问禅道。禅道里的单据留痕在他自己名下——所以交付时说「这是你提交的」有据可依。但仍要**回读核对创建者字段 `openedBy`**：不是本人就如实说是谁，并说明原因（多半是单据走了宿主 MCP 工具那条服务端固定身份的路，见 `setup.md` 的「禅道 MCP：只给人手动查看」）。`feedbackBy` 是业务字段（反馈者），禅道不自动记录它，**不能拿它核对提交人**。

用户问「我提交的全部反馈」时：

> 现在是用当前登录的账号在查，`openedbyme` 就是这个账号下提交的记录；不过你能看到的范围取决于禅道给你的权限，看不到的（别人的单据、没开权限的产品）我查不出来。

不要说「禅道里所有重复都没有」；也不要把别人的单据说成用户自己的；提交人不是用户本人时，要说清楚。缺陷单的提交人字段是 `openedBy`，同样要核对。
