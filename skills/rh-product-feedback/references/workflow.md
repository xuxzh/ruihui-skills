# 工作流与话术

示例数据均为虚构。流程主干见 `SKILL.md`，本文给出逐步细节与输出样例。

## 总览

```
用户表达
  │
  ├─ 提交 ──► 自检与登录 ─► 收要素 ─► 草稿 ─► 查重 ─► 确认 ─► 创建 ─► 回读 ─► 交付
  ├─ 查询 ──► 自检与登录 ─► 定位反馈单 ─► 读字段与 actions ─► 三段式解释
  └─ 补充 ──► 自检与登录 ─► 读原文 ─► 追加草稿 ─► 确认 ─► 更新 desc ─► 回读
```

## F0 首次接入（连接禅道）

用户第一次用，或宿主里还没有禅道工具时。**地址不回显，凭据不由 agent 写**。

**技能没装**（宿主里找不到这个技能）：

> 禅道反馈助手还没装上，两步：
>
> 1. 装技能：`npx skills add xuxzh/ruihui-skills --skill rh-product-feedback --global`
> 2. 再跑这条命令——它会登记禅道 MCP，并让你输入自己的禅道账号和密码（密码不回显，只写在你自己的机器上）：
>
> ```bash
> bash ~/.claude/skills/rh-product-feedback/scripts/install.sh
> ```
>
> 跑完请退出重开一下 Claude Code，然后说「验证一下禅道连接」。

**技能装了但禅道工具不可用**（宿主里没有 `zentao` 工具）：只给第 2 步。

用户重开后按 0.3 登录并自检，然后**如实说明两件事**：

- 凭据已写入本机，本次登录用的是它；
- **当前禅道 MCP 恒以服务端固定身份服务**，所以反馈单的提交人暂时不是本人（见 `zentao-mcp.md` 的「实测偏差」）。

用户说「好了」或直接说业务诉求，都不再多问。自检通过时不插入额外的「自检报告 → 等确认」往返。

脚本跑完仍连不上、且 `zentao` 条目被宿主回写覆盖时：

> 地址被宿主覆盖了，我再写一次；还不行的话，请你再跑一次那条命令。

仍然不行 → 让用户自己跑 `install.sh`（地址会自己从技能包里读，不进对话），或让用户去禅道 Web 端提交。

## F1 提交反馈

### 1. 收要素

按 `feedback-templates.md` 判定类型与必填项，一次问全缺失项；呈现格式按同文件的「追问格式」。

对话样例：

> ❓ **Q1** - **这是在哪个页面/入口操作时出现的？**（写不出入口，开发没法复现）
>
> a. 设备管理列表页
> b. 设备管理列表页 → 导出按钮
> c. 设备详情页
> d. 其他（写下页面名）
>
> ➡️ **建议 b**：设备管理列表页的导出按钮。
> 理由：你刚才说的就是导报表没反应，入口越具体开发越能直接定位。
>
> 回复：回一个字母（b）；也可以说「按建议」，我就按 b 继续。
>
> ---
>
> ❓ **Q2** - **期望的正确结果是什么？**（验收标准）
>
> ➡️ **建议**：导出 Excel 文件；导不出时给一条明确的失败原因（哪个字段不合法、哪条数据有问题）。
> 理由：这两条都能判定通过或失败；「别再没反应」判不了。
>
> 回复：回一句就行；也可以说「按建议」。

### 2. 草稿

草稿要展示到用户能逐字判断的程度：

```
类型：Bug
所属产品：示例产品 A（product id: 101）
标题：设备列表导出按钮点击后无响应

描述：
【业务场景】
运维人员在设备管理页导出月度报表。

【复现步骤】
1. 打开「设备管理」
2. 选择时间范围后点「导出」
3. 页面无任何变化，控制台无报错

【实际结果】
点击后无响应，也无失败提示。

【预期结果】
应导出 Excel 文件，或给出明确的失败原因。

【影响范围】
阻断月度报表导出。

【环境】
用户未提供
```

### 3. 查重

调用 `get_products_productID_feedbacks`（`recPerPage=100`，最多 3 页），客户端按标题关键词匹配。

输出样例：

> 在你可见的 42 条反馈中发现 1 条相近记录：
> - #318「设备列表导出无响应」— 状态 wait — 2026-03-04
>
> ❓ **Q3** - **这条反馈是新建还是复用？**（禅道里最终是 1 条还是 2 条）
>
> a. 新建一条
> b. 在 #318 上补充说明
> c. 都不是
>
> ➡️ **建议 b**：在 #318 上补充说明。
> 理由：#318 记的就是同一个现象，禅道里留两条会让评审各看一半、容易漏掉；你这条要是还带了它没写过的信息（报错原文、发生时段），在补充里一并写上就行。
>
> 回复：回一个字母（b）；也可以说「按建议」，我就按 b 继续。

措辞边界：说「在你可见的 42 条中未发现重复」，不要说「禅道里没有重复」——可见范围由当前账号的禅道权限决定。

### 4. 确认

用户回复「新建」即可视为对当前草稿的明确确认。回复只有「嗯」且尚未展示草稿时，先展示草稿再问一次。

### 5. 创建

```json
{"payload": {"product": 101, "title": "设备列表导出按钮点击后无响应", "desc": "<草稿描述全文>", "type": "bug"}}
```

只发一次。

### 6. 回读

`get_feedbacks_feedbackID`（用返回的 `id`）→ 核对 `product` / `title` / 完整 `desc` / `actions` 里的 `opened`。

```
✓ 创建成功，反馈 #421
状态：wait（待评审）
负责人：未指派
操作流水：opened（2026-03-11 10:22）
```

回读不到或内容不一致 → 见 `error-handling.md`，不要重新创建。

创建请求超时、断连时也一样：重查该产品的反馈，只认「基线之外、唯一、回读完全一致」的那条。

```
✓ 创建请求没拿到确认，但查询核实到已创建：反馈 #421（已回读一致）

⚠ 未确认是否已写入：复查没找到本次写入的新记录，也没有重复创建。请到禅道核对后再决定要不要重新提交。

⚠ 无法唯一确认：查到 2 条可能本次创建的记录（#421、#423），请到禅道核对哪条是你的。我没有重复创建。
  链接：<禅道 Web 地址>/feedback-view-421.html
  链接：<禅道 Web 地址>/feedback-view-423.html
```

### 7. 交付

```
已提交反馈 #421（示例产品 A）
- 标题：设备列表导出按钮点击后无响应
- 类型：Bug
- 当前状态：wait（待评审），未指派负责人
- 提交人：以回读到的反馈单提交人为准（当前 MCP 可能是服务端账号，不是本人，见 `zentao-mcp.md` 的「实测偏差」）
- 链接：<禅道 Web 地址>/feedback-view-421.html（读不到 `zentaoWebUrl` 就不给这一行，只给编号）
下一步：等评审结果；要补充信息随时说「补充反馈 #421 ...」
```

## F2 查询反馈

### 定位

- 给了编号 → 直接 `get_feedbacks_feedbackID`。
- 给了标题或产品 → `get_products_productID_feedbacks` 分页拉取 + 客户端匹配，列候选让用户选编号。

### 输出格式

```
反馈 #421（示例产品 A）
- 标题：设备列表导出按钮点击后无响应
- 当前状态：wait（待评审）
- 负责人：未指派
- 提交人：当前登录账号
- 处理时间线：
  · 2026-03-11 10:22 张工 opened
- 结论字段（result / solution）：空
```

## F3 解释处理进度

三段式，段落之间明确分开：

```
事实
- status = review，说明已进入评审
- actions 最后一条是 2026-03-12 09:40 张工（评审人）review，comment 为空
- reviewedBy = 张工，reviewedDate = 2026-03-12
- plan 与 version 均为空

推断
- 评审动作已发生，但 result / solution 仍为空，推断评审尚未给出结论（推断依据：结论字段为空且评审时间已过）

无法确定
- 没有排期记录的原因——禅道里没有这个字段，也没有评论说明拒绝或延期的理由
```

关键纪律：**没有排期 ≠ 被拒绝**。前者是事实，后者只能是推断，且必须写明是推断。

## F4 补充反馈

### 追加草稿

原文完整保留：

```
<原有 desc 全文>

──────────────
【补充说明 · 2026-03-12 · 用户口述，AI 整理】
【复现步骤补充】
补充：必须先选中至少一行设备，点「导出」才复现；不选直接点没反应。
【预期结果补充】
导出 Excel，文件名格式 yyyyMM设备清单.xlsx
```

### 写前复核

用户确认之后、写入之前，再读一次这条反馈，核对产品、标题、原始 `desc` 是否仍与生成草稿时一致。

```
⚠ 这条反馈在你确认期间被改过，我还没写入。下面是它现在的原文和我重新合并后的草稿，确认后我再更新：
<当前原文>
<重新合并后的完整描述>
```

### 更新

```json
{"payload": {"product": 101, "title": "设备列表导出按钮点击后无响应", "desc": "<原文 + 追加段>"}}
```

`product` 与 `title` 沿用当前值（禅道要求这两个字段）。只发一次更新请求。

### 回读

把回读的 `desc` 与完整预期描述归一化换行后逐字比较，并确认 `actions` 这次**新增**了 `edited`（历史上有过 `edited` 不算）。

```
已更新反馈 #421（追加 1 段说明）
- 原文保留，描述从 320 字增加到 512 字
- 操作流水新增：edited（当前登录账号）
```

更新超时或返回无法解析时只读核实，不重放更新；核实不了就说「未确认是否已更新」。

## 身份与权限的措辞

当前会话是**当前登录账号**在操作。禅道里的反馈单留痕在这个账号名下——但当前 MCP 的登录接口不校验凭据、恒以服务端身份服务（见 `zentao-mcp.md` 的「实测偏差」），所以「留痕在本人名下」这句话要等 MCP 修好才成立；在那之前，回读到的提交人是谁就如实说是谁。

用户问「我提交的全部反馈」时：

> 现在是用当前登录的账号在查，`openedbyme` 就是这个账号下提交的记录；不过你能看到的范围取决于禅道给你的权限，看不到的（别人的单据、没开权限的产品）我查不出来。

不要说「禅道里所有重复都没有」；也不要把别人的单据说成用户自己的；提交人不是用户本人时，要说明清楚。
