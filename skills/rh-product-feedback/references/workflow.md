# 工作流与话术

示例数据均为虚构。流程主干见 `SKILL.md`，本文给出逐步细节与输出样例。

```
  ├─ 提交反馈 ─► 自检与登录 ─► 收要素 ─► 草稿 ─► 查重 ─► 确认 ─► 创建 ─► 回读 ─► 交付
  ├─ 提交缺陷 ─► 自检与登录 ─► 收要素 ─► 草稿 ─► 查重 ─► 确认 ─► 创建 ─► 回读 ─► 交付
  ├─ 查询 ──► 自检与登录 ─► 定位单据 ─► 读字段与 actions ─► 三段式解释
  └─ 补充 ──► 自检与登录 ─► 读原文 ─► 追加草稿 ─► 确认 ─► 更新正文 ─► 回读
```

## F0 首次接入（连接禅道）

用户第一次用，或宿主里还没有禅道工具时。**地址不回显，凭据不由 agent 写**。

**技能没装**（宿主里找不到这个技能）：让用户把安装提示词发给你——提示词见 [setup.md](setup.md)「安装提示词」，它让当前宿主自己装技能、自己登记禅道 MCP。

**技能装了但禅道工具不可用**（宿主里没有 `zentao` 工具）：走 0.2 的 A 路径，在**当前宿主**里登记禅道 MCP（位置与写法见 [setup.md](setup.md)「各宿主配置」），再请用户自己写入凭据。

自检用查询器 `products`（脚本自己换当前账号的令牌），然后**如实说明两件事**：

- 凭据已写入本机，本次操作用的是它换出来的、属于终端用户账号的令牌；
- 单据会留痕在终端用户自己名下——回读到的提交人应当就是他本人；不是本人就如实说明（见 `zentao-mcp.md` 的「身份与认证」）。

用户说「好了」或直接说业务诉求，都不再多问。自检通过时不插入额外的「自检报告 → 等确认」往返。

登记完仍连不上、且 `zentao` 条目被宿主回写覆盖时：

> 地址被宿主覆盖了，我再写一次；还不行的话，请退出重开一下这个 Agent。

仍然不行 → 让用户按 [setup.md](setup.md)「各宿主配置」自己改宿主配置里的 `zentao` 条目（地址从技能包的 `config.local.json` 读），或让用户去禅道 Web 端提交。

## F1 提交反馈

### 1. 收要素

按 `feedback-templates.md` 判定类型与必填项，一次问全缺失项；呈现格式按同文件的「追问格式」。

对话样例：

> ❓ **Q1** - **这是在哪个页面/入口操作时出现的？**（写不出入口，开发没法复现）
>
> a. 设备管理列表页
> b. 设备管理列表页 → 导出按钮
> c. 设备详情页
> d. 其他（写下页面名）
>
> ➡️ **建议 b**：设备管理列表页的导出按钮。
> 理由：你刚才说的就是导报表没反应，入口越具体开发越能直接定位。
>
> 回复：回一个字母（b）；也可以说「按建议」，我就按 b 继续。
>
> ---
>
> ❓ **Q2** - **期望的正确结果是什么？**（验收标准）
>
> ➡️ **建议**：导出 Excel 文件；导不出时给一条明确的失败原因（哪个字段不合法、哪条数据有问题）。
> 理由：这两条都能判定通过或失败；「别再没反应」判不了。
>
> 回复：回一句就行；也可以说「按建议」。

### 2. 草稿

草稿要展示到用户能逐字判断的程度：

```
类型：Bug
所属产品：示例产品 A（product id: 101）
标题：设备列表导出按钮点击后无响应

描述：
【业务场景】
运维人员在设备管理页导出月度报表。

【复现步骤】
1. 打开「设备管理」
2. 选择时间范围后点「导出」
3. 页面无任何变化，控制台无报错

【实际结果】
点击后无响应，也无失败提示。

【预期结果】
应导出 Excel 文件，或给出明确的失败原因。

【影响范围】
阻断月度报表导出。

【环境】
用户未提供
```

### 3. 查重

入口脚本 `node <技能目录>/scripts/zentao.mjs dup --kind feedback --product <产品ID> --title "<用户的标题>"`：脚本把标题切成**中文二元组**（英文按词），生成「组内且、组间或」的关键词变体组交给禅道 CLI 在客户端匹配，只在标题里找——**正文里出现的词不算命中**。词序不同也算重复：用户说「切换语言功能失效」，禅道里写的「语言切换功能失效」会被命中。

脚本给三样东西：候选表格（编号、标题、状态、负责人、匹配度）、覆盖范围（`# 覆盖范围：…`）、查重基线（最后一行 JSON 的 `baseline`，是本次扫描到的全部单据 ID）。

输出样例：

> 在你可见的 42 条反馈中发现 1 条相近记录：
> - #318「设备列表导出无响应」— 状态 wait — 负责人 张工
>
> ❓ **Q3** - **这条反馈是新建还是复用？**（禅道里最终是 1 条还是 2 条）
>
> a. 新建一条
> b. 在 #318 上补充说明
> c. 都不是
>
> ➡️ **建议 b**：在 #318 上补充说明。
> 理由：#318 记的就是同一个现象，禅道里留两条会让评审各看一半、容易漏掉；你这条要是还带了它没写过的信息（报错原文、发生时段），在补充里一并写上就行。
>
> 回复：回一个字母（b）；也可以说「按建议」，我就按 b 继续。

措辞边界：说「在你可见的 42 条中未发现重复」，不要说「禅道里没有重复」——可见范围由当前账号的禅道权限决定。

取舍：标题很长时（两两配对会超过 40 组），脚本改用相邻窗口（相邻二元组 + 长度为 3 的滑动窗口）匹配，组数不再平方增长；代价是共有的词在标题里隔得远时可能匹配不到，这时把 `--title` 换成最有区分度的几个字再扫一次。

### 4. 确认

用户回复「新建」即可视为对当前草稿的明确确认。回复只有「嗯」且尚未展示草稿时，先展示草稿再问一次。

### 5. 创建

先把载荷写进临时文件，再交入口脚本；**正文只走文件，不进命令行参数**。

```json
{"product": 101, "title": "设备列表导出按钮点击后无响应", "type": "bug", "desc": "<草稿描述全文>"}
```

```bash
node <技能目录>/scripts/zentao.mjs feedback-create --payload-file /tmp/rh-zentao-payload.json
```

- `product` 写**整数**（字符串形态会被服务端静默忽略）；`desc` 是**纯文本**描述，不写 HTML 标签；`source` / `module` 不填。
- 反馈者 `feedbackBy` **不用你填**：入口脚本按当前禅道账号显式补上——这台实例的禅道不自动记录反馈者，不显式写就永远没有反馈者。载荷里填了别的账号会被拒绝。
- **只发一次**：脚本只发一次创建请求，禅道创建没有幂等键，不要自己再补一次。临时文件由脚本用完即删。
- 反馈单**不附带建缺陷单**：禅道没有「反馈转缺陷」的关联字段，一次诉求只建一张单。

### 6. 回读

`feedback-create` 已经按返回的编号做过回读核对：`product` / `title` / 完整 `desc`（纯文本，只归一化换行与行尾空白）/ 反馈者 / **创建者字段 `openedBy`** / `actions` 里**本次新增**的 `opened`（历史上存在过不算）。它把结论、交付要素与核对依据打成一行 JSON：

```
{"ok":true,"kind":"feedback","id":421,"title":"设备列表导出按钮点击后无响应","status":"active","product":101,"type":"bug","feedbackBy":"zhangsan","openedBy":"zhangsan","submitterField":"openedBy","submitterIsCurrentAccount":true,"url":"<禅道 Web 地址>/feedback-view-421.html","verified":"readback"}
```

- **提交人核对看的是创建者字段 `openedBy`**：这台实例的禅道不自动记录反馈者（`feedbackBy` 可能恒为空），拿它核对会得出「提交人是别人」的错结论。回读里取不到 `openedBy`（字段名与本实例不一致）时，`mismatches` 里会出现「创建者字段（openedBy）」——**如实报告，不要猜哪个字段是提交人**。
- `verified: "readback"` → 回读通过。`verified: "query"` → 创建回执丢了（超时 / 断连），结论来自重查该产品后唯一一致的新记录，**交付时要说明「编号来自查询核实」**。
- `ok:false` + `created:true` + `mismatches` → 单据建出来了但内容对不上：**不要重建**，把不一致项与单据现状告诉终端用户。
- `ok:false` + `uncertain:true` → 是否建成**未确认**：不重发，把 `candidates` 列给终端用户并请他自己在禅道里看一眼；**不要把「没查到」说成「没创建」**。
- 终端用户要细节时，再用查询器 `feedback --id <ID>` 读一遍正文、流水与历史。

回读不到或内容不一致 → 见 `error-handling.md`，不要重新创建。

创建请求超时、断连时也一样：重查该产品的反馈，只认「基线之外、唯一、回读完全一致」的那条。

```
✓ 创建请求没拿到确认，但查询核实到已创建：反馈 #421（已回读一致）

⚠ 未确认是否已写入：复查没找到本次写入的新记录，也没有重复创建。请到禅道核对后再决定要不要重新提交。

⚠ 无法唯一确认：查到 2 条可能本次创建的记录（#421、#423），请到禅道核对哪条是你的。我没有重复创建。
  链接：<禅道 Web 地址>/feedback-view-421.html
  链接：<禅道 Web 地址>/feedback-view-423.html
```

### 7. 交付

```
已提交反馈 #421（示例产品 A）
- 标题：设备列表导出按钮点击后无响应
- 类型：Bug
- 当前状态：wait（待评审），未指派负责人
- 反馈者：zhangsan（禅道里 `feedbackBy` 记的就是你本人）
- 提交人：zhangsan（回读到的 `openedBy`，创建者字段，就是你自己）
- 链接：<禅道 Web 地址>/feedback-view-421.html（读不到 `zentaoWebUrl` 就不给这一行，只给编号）
下一步：等评审结果；要补充信息随时说「补充反馈 #421 ...」
```

- **反馈者与创建者都是本人** → 说「这条反馈单的反馈者与提交人都是你」。
- **两者不一致**（如反馈者字段记的是 `zhangsan`、创建者是 `lisi`）→ 如实说「反馈者字段记录的是 zhangsan，创建者（留痕主体）是 lisi」，**不粉饰**。
- `submitterIsCurrentAccount` 为 `false` → 禅道里这条单据的提交人是别人，如实说明（见 `zentao-mcp.md` 的「身份与认证」），不要把服务端的提交人当成终端用户本人。
- `url` 为 null（技能包没配 `zentaoWebUrl`）就不给链接，只给编号并说明原因。

## F1b 提交缺陷单

缺陷单会进开发流程，所以草稿与确认比反馈单更明确。

### 1. 收要素

按 `bug-templates.md` 判定必填项。**禅道字段不追问**（严重程度、优先级、版本、执行、模块走默认值）。

选品优先级：用户这次明说的产品 > 本机默认产品 > 追问一次。只有明说与默认都没有时才问：

> ❓ **Q1** - **这条缺陷记到哪个产品下？**（禅道按产品分派开发）
>
> a. MOMV2.0（示例产品 A）
> b. 瑞辉智能报表平台（示例产品 B）
>
> ➡️ **建议 a**：你前面说的就是这个系统的功能。
> 理由：产品错了单子会落到别的团队名下，白等一轮。
>
> 回复：回一个字母（a）；也可以说「按建议」，我就按 a 继续。

### 2. 草稿

纯文本版给用户看，末尾带声明：

```
即将创建的是禅道正式缺陷单（会进入开发流程），不是反馈单。

所属产品：MOMV2.0（product id: 1）
所属项目：MOMV2.0-RD
标题：设备列表导出按钮点击后无响应
严重程度 / 优先级：3 / 3（默认值）
影响版本：trunk（默认值）
缺陷类型：codeerror
负责人：未指派（随包默认不指派；生效值是产品 QD 时写「产品 QD：majiawei（马嘉炜）」，用户指名就写他的账号）

正文：
【步骤】
1. 打开「设备管理」
2. 选择时间范围后点「导出」
3. 页面无任何变化，控制台报 500

【实际结果】
点击后无响应，控制台报 500。

【预期结果】
应导出 Excel 文件，或给出明确的失败原因。

【业务场景】
仓管每天下班前导出对账。

【影响范围】
阻断月度报表导出。

【环境】
用户未提供
```

### 3. 查重

入口脚本 `node <技能目录>/scripts/zentao.mjs dup --kind bug --product <产品ID> --title "<用户的标题>"`：脚本把标题切成**中文二元组**（英文按词），生成「组内且、组间或」的关键词变体组交给禅道 CLI 在客户端匹配，只在标题里找——**正文里出现的词不算命中**。词序不同也算重复：用户说「切换语言功能失效」，禅道里写的「语言切换功能失效」会被命中。**同一产品顺带再扫一次反馈单**（`--kind feedback`），两边的候选都要给，避免同一件事在两个模块各建一张。

脚本给三样东西：候选表格（编号、标题、状态、负责人、匹配度）、覆盖范围（`# 覆盖范围：…`）、查重基线（最后一行 JSON 的 `baseline`，是本次扫描到的全部单据 ID；基线之外的编号才可能是本次新建）。

> 在你可见的 300 条缺陷中发现 1 条相近记录：
> - #1934「设备列表导出按钮点击后无响应」— 状态 active — 负责人 张工
>
> 反馈单里也有 1 条相近记录：#318「设备列表导出无响应」。
>
> ❓ **Q2** - **这条缺陷是新建还是复用？**
>
> a. 新建一条缺陷单
> b. 在 #1934 上补充
> c. 都不是
>
> ➡️ **建议 b**：在 #1934 上补充说明。
> 理由：#1934 记的就是同一个现象，它已经有负责人跟进；你这条要是带了它没写过的信息（报错原文、发生时段），在补充里一并写上。
>
> 回复：回一个字母（b）；也可以说「按建议」，我就按 b 继续。

措辞边界：说「在你可见的 N 条中未发现重复」，不说「禅道里没有重复」——可见范围受当前账号的权限限制。

取舍：标题很长时（两两配对会超过 40 组），脚本改用相邻窗口（相邻二元组 + 长度为 3 的滑动窗口）匹配，组数不再平方增长；代价是共有的词在标题里隔得远时可能匹配不到，这时把 `--title` 换成最有区分度的几个字再扫一次。

### 4. 确认

用户回复「新建」即可视为对当前草稿的明确确认。草稿里必须带「即将创建的是禅道正式缺陷单（会进入开发流程）」这一行。

只回「嗯」「行吧」而没看到草稿 → **先把草稿贴出来再问一次**；草稿改过（换了产品、加了正文、改了负责人）→ 重新贴新草稿再确认。没拿到明确确认，不调写入命令。

### 5. 创建

先把载荷写进临时文件，再交入口脚本；**正文只走文件，不进命令行参数**。

```json
{"productID": 1, "title": "设备列表导出按钮点击后无响应", "openedBuild": ["trunk"], "severity": 3, "pri": 3, "type": "codeerror", "steps": "<正文 HTML>"}
```

```bash
node <技能目录>/scripts/zentao.mjs bug-create --payload-file /tmp/rh-zentao-payload.json
```

- 字段名是 `productID`（反馈单是 `product`），`openedBuild` 是字符串数组，`severity` / `pri` 写数字（CLI 不接受字符串）。文件里放请求体本身，不要再套一层 `payload`。
- **只发一次**：脚本只发一次创建请求，禅道创建没有幂等键，不要自己再补一次。临时文件由脚本用完即删。
- 负责人不写在这个载荷里：入口脚本按「默认负责人」配置补——随包默认 `""` 补空串（不指派，挡住禅道侧默认指派），代码兜底 `"qd"` 不带这个字段（由禅道按产品的 QD 指派），用户明确指名才写他的账号。见 [setup.md](setup.md)「默认负责人」。
- 脚本写入前先拍一次查重基线（该产品下的缺陷编号），结果不确定时只用它判断哪些编号是本次新建的。

### 6. 回读

`bug-create` 已经按返回的编号做过回读核对：`product` / `title` / `steps`（**剥标签 + 归一化空白**后逐字比较）/ `openedBuild`（`trunk` 与「主干」归一化）/ `severity` / `pri` / `assignedTo`，以及 `actions` 里**本次新增**的 `opened`（历史上存在过不算）。它把结论、交付要素与核对依据打成一行 JSON：

```
{"ok":true,"kind":"bug","id":1935,"title":"设备列表导出按钮点击后无响应","status":"active","assignedTo":"","assigneeSource":"package","openedBy":"zhangsan","url":"<禅道 Web 地址>/bug-view-1935.html","verified":"readback"}
```

- `verified: "readback"` → 回读通过。`verified: "query"` → 创建回执丢了（超时 / 断连），结论来自重查该产品后唯一一致的新记录，**交付时要说明「编号来自查询核实」**。
- `ok:false` + `created:true` + `mismatches` → 单据建出来了但内容对不上：**不要重建**，把不一致项与单据现状告诉终端用户（该改的自己改不了：技能不流转、不改单据）。
- `ok:false` + `uncertain:true` → 是否建成**未确认**：不重发，把 `candidates` 列给终端用户并请他自己在禅道里看一眼；**不要把「没查到」说成「没创建」**。
- 终端用户要细节时，再用查询器 `bug --id <ID>` 读一遍正文、流水与历史。

负责人的生效值：`assigneeSource` 为 `qd` 时用查询器 `qd --product <产品ID>` 取 QD 账号与姓名对照回读到的 `assignedTo`（对不上就如实说明，不要改单据）；为 `package` / `local` / `user` 时断言 `assignedTo` 与载荷一致（`""` 就是未指派）。

### 7. 交付

```
已提交缺陷单 #1935（MOMV2.0）
- 标题：设备列表导出按钮点击后无响应
- 所属项目：MOMV2.0-RD
- 严重程度/优先级：3 / 3
- 影响版本：trunk
- 当前状态：active
- 负责人：未指派（随包默认未指派）
- 提交人：zhangsan（回读到的 openedBy，就是你自己）
- 链接：<禅道 Web 地址>/bug-view-1935.html
下一步：等开发认领；要补充信息随时说「补充缺陷 #1935 ...」
```

负责人一栏按 `assigneeSource` 说清来源：`user` 终端用户指名 / `local` 本机默认 / `package` 随包默认未指派 / `qd` 产品 QD。`openedBy` 与当前禅道账号不一致时如实说明「禅道里这条单据的提交人是 <另一个人>」。`url` 为 null（技能包没配 `zentaoWebUrl`）就不给链接，只给编号并说明原因。

### 默认负责人

用户说「以后提 bug 默认不指派」「默认都指给张三」时，把值合并写进偏好文件的 `bugAssignee`（别覆盖文件里已有的 `defaultProduct`），回读复核后告知用户。取值含义与生效顺序见 [setup.md](setup.md)「默认负责人」。

缺省是产品 QD 承接；用户想看到承接人是谁时，查询器 `qd --product <产品ID>` 给出 QD 账号、姓名与账号是否还能用。

### 默认产品

用户说「默认产品是 <产品名>」时：

1. 查询器 `products --match <产品名>` 确认它在当前账号可见范围内；不可见就如实说明并让用户换一个。
2. 把要写的内容给用户确认（产品 id + 名称）。
3. 写入用户机器上的偏好文件 `~/.config/rh-zentao/preferences.json`：

   ```json
   { "defaultProduct": { "id": 1, "name": "MOMV2.0" } }
   ```

4. 回读复核文件内容，再告诉用户「默认产品已设为 <名称>」。

**绝不写进技能包的 `config.local.json`**——那会随技能包分发给所有用户，把一个人的产品变成别人的默认值。

使用时的规则：默认产品只是默认值，用户这次说了别的产品就用用户说的；默认产品当前不可见就如实说明并列出可见产品，不静默换产品建单。

## F2 查询单据

### 定位

- 给了编号 → 看上下文判断单据类型：缺陷 `node <技能目录>/scripts/zentao.mjs bug --id <ID>`，反馈 `feedback --id <ID>`。
- 给了产品或标题 → 先列单据，再让他挑编号打开：

```bash
node <技能目录>/scripts/zentao.mjs bugs --product 29 --match 切换语言   # 缺陷单
node <技能目录>/scripts/zentao.mjs feedbacks --product 29 --status wait  # 反馈单
```

列表是「一次拉全量 + 字段投影 + 客户端筛选」：脚本用 `--all` 把所有页取完、只留投影字段、在进程内按 `--status` / `--match` 过滤，所以表头的「可见 N 条」是当前账号在这个产品下能看到的**全部**，不是第一页；`--match` 只匹配标题，正文里的词不算命中。

### 输出格式

列表（表格，十几行；默认 10 条）：

```
# 缺陷（产品 29 可见 12 条，筛选后 2 条）
1945	切换语言后页面文案仍是中文	resolved	dev-a	2/2
1946	语言切换不生效	closed	dev-b	3/2
```

详情（一行 JSON，节选）：

```json
{"ok":true,"kind":"bug","id":1945,"product":29,"title":"切换语言后页面文案仍是中文","status":"resolved","assignee":"dev-a","openedBy":"zhangsan","openedDate":"2026-03-10 09:00:00","processor":"dev-a","processedDate":"2026-03-12 15:30:00","resolution":"fixed","body":"[步骤] 打开设置 → 切换语言\n[结果] 文案没变","actions":[{"id":19451,"action":"opened","actor":"zhangsan","date":"2026-03-10 09:00:00","comment":"（空）","changes":[]},{"id":19452,"action":"resolved","actor":"dev-a","date":"2026-03-12 15:30:00","comment":"（空）","changes":[{"field":"status","from":"active","to":"resolved"}]}]}
```

讲给用户时把 JSON 里的事实转成人能读的几行，样例：

```
缺陷 #1945（示例产品 A）
- 标题：切换语言后页面文案仍是中文
- 当前状态：resolved（已解决），结论 resolution = fixed（已修复）
- 负责人：dev-a；处理人：dev-a，处理时间：2026-03-12 15:30
- 提交人：zhangsan，2026-03-10 09:00 提交
- 处理时间线：
  · 2026-03-12 15:30 dev-a resolved（status：active → resolved）
  · 2026-03-10 09:00 zhangsan opened
```

## F3 解释处理进度

三段式，段落之间明确分开：

```
事实
- status = resolved，resolution = fixed（都是禅道字段原值）
- 负责人 assignedTo = dev-a
- 处理人 resolvedBy = dev-a，处理时间 resolvedDate = 2026-03-12 15:30
- 流水 2 条：2026-03-10 09:00 zhangsan opened；2026-03-12 15:30 dev-a resolved 并把 status 从 active 改成 resolved
- plan 与 version 字段为空

推断（每条都标注是推断）
- 推断：这条已经改完、在等验证（依据：resolution = fixed，且之后没有新的流水）
- 推断：下个版本能带上（依据：状态已到 resolved，但禅道里没有版本字段，这条推断可信度低）

无法确定
- 禅道里没有排期记录，也没有评论说明何时上线
- 验证人是谁、什么时候验：禅道里没有这个字段
```

关键纪律：**没有排期 ≠ 被拒绝**。前者是事实，后者只能是推断，且必须写明是推断。事实段落里也不要解释字段含义之外的因果（「因为负责人忙」不是事实）；流水里带 `"new": true` 的是本次写入新增的动作，其余是历史动作，两边不要混着讲。

反馈单走同一套三段式，只是字段名不同：处理人/处理时间取 `processor` / `processedDate`（禅道字段 `processedBy` / `processedDate`），结论取 `resolution`（禅道字段 `solution`），另有 `reviewer` / `reviewedDate`（评审人、评审时间）——评审已发生但 `resolution` 为空时，只能说「禅道里还没有结论」，不能替他下结论。

反馈单改 `desc`，缺陷单改 `steps`（追加 HTML 段落），其余步骤一样。

### 追加草稿

原文完整保留：

```
<原有 desc 全文>
```

### 写前复核


### 更新

```json

```

`product` 与 `title` 沿用当前值（禅道要求这两个字段）。只发一次更新请求。

## F5 正文带图片

用户给了截图（或在对话里粘贴了图片）时，建单之后多两步：**传图 → 更新正文**。顺序不能颠倒——禅道的上传要挂在已经存在的单据上，所以一定是先建单。

### 1. 拿到图片

宿主把粘贴的图片存成本机文件，并把路径贴进消息（pi 粘贴图片会写进临时目录并把路径贴出来）。先 `read` 这个图片文件，确认它对应正文里的哪一段描述。

### 2. 图片拿不到时

```
你发的这张图我这边拿不到文件（只有截图，没有能读到的路径）。两个办法：
- 把图片存到本机，把路径发我，我传上去；
- 我先按文字把单据建好，你到禅道里手动补图。
```

不要编造路径，也不要把「用户描述了图里有什么」当成图片已经放上去。

### 3. 传图

```bash
node <技能目录>/scripts/zentao-upload.mjs --file <图片路径> --object-type feedback --object-id <反馈 ID>
```

缺陷单把 `--object-type` 换成 `bug`。脚本输出：

```
# 上传成功
文件 ID：6530
图片引用：<img src="/index.php?m=file&f=read&t=png&fileID=6530" alt="file-read-6530.png" />
字节核对：本地 70，禅道 70，一致
挂载对象：feedback #421
```

脚本自己回读过字节，输出「一致」才算传上去。

### 4. 更新正文

把图片引用放进正文对应位置，正文其余部分原样保留，按 F4 的可靠路径走（草稿 → 用户确认 → 写前复核 → 更新 → 回读）。反馈单改 `desc`，缺陷单改 `steps`。

草稿给用户看时用纯文本版，图片位置写「[截图 1]」这类说明：

```
即将更新的正文（反馈 #421）：
【业务场景】
仓管每天下班前导出对账。
【复现步骤】
1. 打开设备列表页
2. 点「导出」
3. 页面无响应
[截图 1]
【实际结果】
导出无响应
```

### 5. 回读与交付

回读确认正文里有这条图片引用、且引用里的文件 ID 与上传返回的一致。交付时说明正文里带了几张图：

```
已建反馈 #421（瑞辉智能报表平台）
- 标题：导出按钮点击后无响应
- 正文：含 1 张截图（文件 #6530）
- 状态：待评审
```

### 6. 引用标签的形态

正文里的图片引用固定长这样：

```html
<img src="/index.php?m=file&f=read&t=<扩展名>&fileID=<文件 ID>" alt="file-read-<文件 ID>.<扩展名>" />
```

- 用**相对路径**，不要写绝对地址（禅道地址随部署变，写死会在别的环境失效）。
- `t` 是扩展名（小写、不带点），`fileID` 是上传返回的文件 ID。
- 不要用 base64 内联（`data:` 开头的 src）：禅道与消费端都不认这种写法。

### 7. 边界

- 一次诉求挂几张图就传几张，各自带一个标签；不要把多张图拼成一张。
- 上传失败按 [error-handling.md](error-handling.md) 的「图片上传失败」处理：单据已经建好，如实说图没传上去，不重建单据，也不改用文字描述假装图已经放上去。
- 删除单据时图片是否一并清理由禅道决定，技能不承诺。

## 身份与权限的措辞

当前会话是**终端用户自己的禅道账号**在操作：随包脚本用他的凭据换一个属于他的令牌，带着令牌访问禅道。禅道里的单据留痕在他自己名下——所以交付时说「这是你提交的」有据可依。但仍要**回读核对** `feedbackBy` / `openedBy`：不是本人就如实说是谁，并说明原因（多半是单据走了宿主 MCP 工具那条服务端固定身份的路，见 `zentao-mcp.md` 的「身份与认证」）。

用户问「我提交的全部反馈」时：

> 现在是用当前登录的账号在查，`openedbyme` 就是这个账号下提交的记录；不过你能看到的范围取决于禅道给你的权限，看不到的（别人的单据、没开权限的产品）我查不出来。

不要说「禅道里所有重复都没有」；也不要把别人的单据说成用户自己的；提交人不是用户本人时，要说清楚。缺陷单的提交人字段是 `openedBy`，同样要核对。
