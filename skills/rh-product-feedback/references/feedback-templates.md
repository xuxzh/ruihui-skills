# 反馈内容模板与追问规则

草稿用 Markdown 纯文本渲染，禅道描述字段按换行保存。所有示例均为虚构数据。

## 通用结构

```
【类型】Bug / 需求 / 建议
【所属产品】<产品名>（product id: <id>）
【业务场景】<谁、在什么情况下、想完成什么>
【现象 / 期望】<实际发生了什么 / 希望发生什么>
【标题】<一句话概括>
【描述】<正文，见下方模板>
```

标题写法：**现象 + 场景**或**能力 + 场景**，控制在 30 字以内；不写「急」「BUG」「帮我看看」这类无信息量的词。

## Bug 模板

```
【业务场景】
<用户在什么操作下遇到问题；影响谁、影响多大>

【复现步骤】
1. <入口 / 页面 / 操作>
2. <动作>
3. <出现问题的动作>

【实际结果】
<观察到的现象；有报错就贴原文报错>

【预期结果】
<正确应该是什么样>

【影响范围】
<影响的功能 / 影响的人 / 是否阻断>

【环境】
<浏览器、系统、版本、账号角色等；用户没提供就写「用户未提供」>
```

## 需求模板

```
【业务场景】
<谁、在什么流程中遇到什么阻碍>

【期望能力】
<希望系统能做什么，用一句话说清边界>

【期望收益】
<解决后带来什么可观察的变化>

【验收标准】
<怎样算做成了；用户没给就按期望能力反推 1–3 条并标注「AI 建议，待确认」>

【优先级依据】
<用户提到的紧急程度 / 影响面；没提就不写>
```

## 建议模板

```
【现状痛点】
<现在哪里别扭 / 效率低在哪>

【期望改进】
<希望怎么改>

【替代方案 / 收益】
<有没有别的做法，或改完能省什么>

【参考】
<用户提到的页面、文档、截图说明；没有就省略这一段>
```

## 补充说明模板（追加到已有描述末尾）

追加时**保留原文不动**，在其后追加：

```

──────────────
【补充说明 · <日期> · 用户口述，AI 整理】
<补充内容：复现步骤 / 业务场景 / 预期结果 / 实际结果 / 其他说明>
```

## 追问规则

追问的判断标准只有一个：**缺了它，禅道里这条反馈就无法被分类、复现或验收**。

| 缺失项 | 是否追问 |
| --- | --- |
| 所属产品（无法从上下文判断） | 追问 |
| Bug 的复现步骤或实际结果 | 追问 |
| 实际结果与预期结果（Bug） | 追问 |
| 需求的期望能力 | 追问 |
| 建议的现状痛点 | 追问 |
| 优先级、严重程度、模块、版本号、负责人 | 不追问；留空并写「用户未提供」 |
| 用户的姓名、邮箱、工号 | 不追问；禅道里记在当前禅道账号上 |

追问方式：**一次问全**，把缺的几项列成清单交给用户；呈现格式见下面「追问格式」。

用户答不上来时，写「用户未提供」继续走流程——草稿里留空即可，不要卡住用户。

## 追问格式

一次问全的那一轮长这样：编号 Q1、Q2 连续排下去，问题之间用 `---` 分隔。每个问题三件套——**问什么、可选什么、建议选哪个**。

| 段 | 写法 |
| --- | --- |
| 问什么 | `❓ **Q1** - **<问题>**（<这个答案会改变草稿里的什么>）` |
| 可选什么 | 互斥选项逐条一行，用小写字母 `a` `b` `c` `d` 标注，每条只写选项本身 |
| 建议选哪个 | `➡️ **建议 <字母>**：<要选什么>`，下一行 `理由：<为什么这样最省事、最可验收>` |
| 怎么回 | `回复：回一个字母（b）；也可以说「按建议」，我就按 b 继续。` |

给建议的两条要求：

- **建议要给具体答案**：从上下文推断出来摆到用户面前（用户已经说过的、常规做法），让他改或确认，不要把问题原样丢回去。
- **理由要落到后果**：写清「选别的会怎样」，不写「建议 b 更好」这种空话。

选项不超过 4 个。排不成互斥选项的（开放题）不给选项，直接给默认答案 + 理由，回复方式改成「回一句就行」。

一轮两个问题的样子：

❓ **Q1** - **日语要覆盖到哪一层？**（决定验收标准）

a. 仅界面文案（菜单、按钮、提示语）
b. 界面 + 报表/导出内容（Excel、PDF、标签打印）
c. 界面 + 业务数据（物料名称、检验标准等由用户维护的数据）
d. 全部以上

➡️ **建议 b**：界面文案 + 报表/导出内容。
理由：界面与导出件通常由同一批人验收，只做界面会留下中文导出物；业务数据要多语言化就得加语言字段、迁历史数据、改维护流程，成本远超收益，通常单独立项。

回复：回一个字母（b）；也可以说「按建议」，我就按 b 继续。

---

❓ **Q2** - **谁在用这套日语界面？**（决定业务场景怎么写）

➡️ **建议**：日本工厂的现场人员——他们日常看界面、扫标签、打印报表。
理由：写清使用人，验收时才知道该找谁确认「做完了没有」；按你提到的日本工厂现场这么写，不对就直接改。

回复：回一句就行；也可以说「按建议」。

## 分类判定

| 信号 | 类型 |
| --- | --- |
| 报错、崩溃、数据不对、功能与设计不符、有明确错误现象 | Bug → `type: bug` |
| 现在做不到、需要新增能力 | 需求 → `type: story` |
| 能做但不好用、体验差、步骤繁琐 | 建议 → `type: advice` |

一句话同时像 Bug 又像需求时（例如「没有这个功能，用起来很难受」），按用户表述的**期望**分类：想要新能力 → 需求；现有能力出错 → Bug；并在草稿里注明分类理由。

## 不做的事

- 不编造版本号、模块、接口名、报错码等用户没提供的事实。
- 不把用户口述的内容改写成「官方结论」；整理后的文本保持用户原意。
- 不在草稿里写情绪化评价（「这破功能」），转成可复现、可验收的描述。
