# 反馈内容模板与追问规则

草稿用 Markdown 纯文本渲染，禅道描述字段按换行保存。所有示例均为虚构数据。

## 通用结构

```
【类型】Bug / 需求 / 建议
【所属产品】<产品名>（product id: <id>）
【业务场景】<谁、在什么情况下、想完成什么>
【现象 / 期望】<实际发生了什么 / 希望发生什么>
【标题】<一句话概括>
【描述】<正文，见下方模板>
```

标题写法：**现象 + 场景**或**能力 + 场景**，控制在 30 字以内；不写「急」「BUG」「帮我看看」这类无信息量的词。

## Bug 模板

```
【业务场景】
<用户在什么操作下遇到问题；影响谁、影响多大>

【复现步骤】
1. <入口 / 页面 / 操作>
2. <动作>
3. <出现问题的动作>

【实际结果】
<观察到的现象；有报错就贴原文报错>

【预期结果】
<正确应该是什么样>

【影响范围】
<影响的功能 / 影响的人 / 是否阻断>

【环境】
<浏览器、系统、版本、账号角色等；用户没提供就写「用户未提供」>
```

## 需求模板

```
【业务场景】
<谁、在什么流程中遇到什么阻碍>

【期望能力】
<希望系统能做什么，用一句话说清边界>

【期望收益】
<解决后带来什么可观察的变化>

【验收标准】
<怎样算做成了；用户没给就按期望能力反推 1–3 条并标注「AI 建议，待确认」>

【优先级依据】
<用户提到的紧急程度 / 影响面；没提就不写>
```

## 建议模板

```
【现状痛点】
<现在哪里别扭 / 效率低在哪>

【期望改进】
<希望怎么改>

【替代方案 / 收益】
<有没有别的做法，或改完能省什么>

【参考】
<用户提到的页面、文档、截图说明；没有就省略这一段>
```

## 补充说明模板（追加到已有描述末尾）

追加时**保留原文不动**，在其后追加：

```

──────────────
【补充说明 · <日期> · 用户口述，AI 整理】
<补充内容：复现步骤 / 业务场景 / 预期结果 / 实际结果 / 其他说明>
```

## 追问规则

追问的判断标准只有一个：**缺了它，禅道里这条反馈就无法被分类、复现或验收**。

| 缺失项 | 是否追问 |
| --- | --- |
| 所属产品（无法从上下文判断） | 追问 |
| Bug 的复现步骤或实际结果 | 追问 |
| 实际结果与预期结果（Bug） | 追问 |
| 需求的期望能力 | 追问 |
| 建议的现状痛点 | 追问 |
| 优先级、严重程度、模块、版本号、负责人 | 不追问；留空并写「用户未提供」 |
| 用户的姓名、邮箱、工号 | 不追问；禅道里统一记在共享服务账号上 |

追问方式：**一次问全**，把缺的几项列成清单交给用户，例如：

> 要写进禅道还差两项，麻烦补充一下：
> 1. 这是在哪个页面/入口操作时出现的？
> 2. 你期望的正确结果是什么？

用户答不上来时，写「用户未提供」继续走流程——草稿里留空即可，不要卡住用户。

## 分类判定

| 信号 | 类型 |
| --- | --- |
| 报错、崩溃、数据不对、功能与设计不符、有明确错误现象 | Bug → `type: bug` |
| 现在做不到、需要新增能力 | 需求 → `type: story` |
| 能做但不好用、体验差、步骤繁琐 | 建议 → `type: advice` |

一句话同时像 Bug 又像需求时（例如「没有这个功能，用起来很难受」），按用户表述的**期望**分类：想要新能力 → 需求；现有能力出错 → Bug；并在草稿里注明分类理由。

## 不做的事

- 不编造版本号、模块、接口名、报错码等用户没提供的事实。
- 不把用户口述的内容改写成「官方结论」；整理后的文本保持用户原意。
- 不在草稿里写情绪化评价（「这破功能」），转成可复现、可验收的描述。
