# rh-product-feedback

把用户的自然语言反馈变成禅道里的**反馈单**（`feedback` 对象），并支持查询、进度解释与补充说明。

禅道 MCP 的工具名、参数包装、字段与枚举都以实测为准 → 读 [references/zentao-mcp.md](references/zentao-mcp.md)。
本文件只保留流程与硬约束；模板、话术与错误处理按需下钻。

## 术语

- **反馈单**：禅道 `feedback` 对象（`post_feedbacks` 创建、`get_feedbacks_feedbackID` 读取）。
- **草稿**：写库前展示给用户确认的结构化内容。
- **回读**：写入后用返回的 ID 重新读取，核对内容与操作流水。
- **当前登录账号**：本会话登录禅道用的那个账号，就是对话里的用户本人；禅道里的反馈单留痕在它名下。
- **接入凭据**：当前登录账号的账号名与令牌（或密码），存在用户自己机器的凭据文件里，agent 不经手。
- **自我安装**：agent 读技能包里的地址配置，按宿主把禅道 MCP 登记进去，再由用户自己写入凭据。

## 0. 会话第一步：环境自检与引导

### 0.1 检测禅道工具是否可用

先确认宿主里存在禅道 MCP 的工具（工具名带 `zentao` 前缀，或至少存在 `post_users_login` 与 `get_products`）。

- **可用** → 继续 0.3。
- **不可用** → 走 0.2 引导安装。**不要**向用户索要禅道地址、IP、端口或账号密码。

### 0.2 引导安装（自我安装）

按 [references/setup.md](references/setup.md) 执行，要点：

1. 从技能包内的 `config.local.json` 读 `mcpUrl`（内网地址写死在这个文件里，**不回显给用户**）。
   - 文件不存在 → 说明拿到的是不含内网配置的公开版技能包：请用户找管理员拿内网版技能包，或直接用禅道 Web 端提交。
2. 按宿主把 MCP server 登记进去（pi：`~/.pi/agent/mcp.json`；Claude Code：用户级 `~/.claude.json`）。已有同名 server 就更新地址，不要覆盖其他配置。
3. 告诉用户需要在本机写入**自己的**禅道凭据，给出 `setup.md` 里的凭据写入命令，让用户自己执行；**不要在对话里索要或回显密码**。
4. 提示用户重启或重连宿主，让新 server 生效，然后回到 0.1 再检测一次。

安装过程只做这些；不要替用户编造地址，不要把凭据写进任何仓库文件。

### 0.3 认证

调用 `post_users_login`，参数包在 `payload` 内：`{"payload": {"account": "<账号>", "password": "<密码或令牌>"}}`。

- 凭据从**本机接入凭据文件**读（位置见 `references/setup.md`）；不要在回复、日志、代码或文档里回显账号、密码、令牌。
- 凭据文件不存在 → 给出写入凭据的命令让用户自己执行，等用户确认已写入后再登录；**不在对话里问密码**。
- 收到 HTTP 401 → 重新登录一次，重试该调用一次；仍失败则停止并报告认证失败（连续失败可能触发禅道账号锁定，不要反复试）。
- 登录成功后会话内沿用该账号的 token，后续调用自动带 token。

完成标准：拿到一次成功登录；或给出明确的认证失败结论与建议动作。

### 0.4 只读自检

认证成功后调一次 `get_products`（只读）确认真的连上了，并用它列出**当前账号可见的产品**——这批产品就是后续选产品的候选范围。失败则按 [references/error-handling.md](references/error-handling.md) 处理。

## 2. 提交反馈

### 2.1 收集要素

按 [references/feedback-templates.md](references/feedback-templates.md) 的模板收集。

- 必备：标题（一句话说清问题）、所属产品、类型、现象或期望、业务场景。
- Bug 追加：复现步骤、实际结果、预期结果。
- 需求追加：期望能力、使用场景。
- 建议追加：现状痛点、期望改进。
- 只追问真正影响分类、复现或验收的信息，一次问全；用户没说的版本号、模块、负责人一律不补写，缺什么就在草稿里写「用户未提供」。

**所属产品**只能从 0.4 列出的**当前账号可见产品**里选。用户说的产品不在其中时，如实说明「你的账号看不到 <产品>，这条反馈暂时无法提交到该产品，请找管理员开权限或换一个产品」，不要报「产品不存在」。

完成标准：模板里每一项都有内容或明确标注缺失。

### 2.2 生成草稿

按模板渲染描述正文。草稿要能独立读懂——用户只看草稿就知道禅道里会存下什么。

### 2.3 查重

禅道 MCP 没有服务端关键词检索，查重靠客户端匹配：

1. `get_products_productID_feedbacks`，`recPerPage=100`，最多取 3 页（上限 300 条）。
2. 在客户端按标题关键词匹配（大小写与空格归一化，取标题中最有区分度的词）。
3. 把候选连同 ID、标题、状态列给用户，让用户选：新建 / 复用候选 / 都不是。

只覆盖拉取到的范围。向用户说明「**在你可见的 N 条**中未发现重复」，而不是「没有重复」——可见范围由当前账号的禅道权限决定。

### 2.4 用户确认

展示：类型、所属产品、标题、描述全文、查重结果。

用户明确确认后才写入。只有「嗯」「行吧」而没看到草稿时，先把草稿给出来再问一次。

### 2.5 创建

`post_feedbacks`，全部字段放进 `payload`：

```json
{"payload": {"product": 42, "title": "<标题>", "desc": "<描述全文>", "type": "bug"}}
```

- `type` 映射：Bug → `bug`，需求 → `story`，建议 → `advice`。
- `product` 是产品 ID（整数，示例里的 42 是占位），先从 `get_products` 确认；`product` 与 `title` 是禅道实际必填项。
- `desc` / `source` / `module` / `feedbackBy` 保持不填：反馈者由禅道按当前登录账号自动记录，填了反而与实际留痕矛盾。
- 只发一次调用。创建接口没有幂等键，同一份 payload 发两次会产生两条记录。

### 2.6 回读校验

用返回的 `id` 调 `get_feedbacks_feedbackID`，核对 `title`、`desc`、`status`，并确认 `actions` 里有 `opened`。

- 一致 → 进入 2.7。
- 不一致或读不到 → 按 [references/error-handling.md](references/error-handling.md) 处理：先查后报，不重复创建。

### 2.7 交付

给出反馈 ID、标题、当前状态、负责人（没有则说明尚未指派）、提交人（当前登录账号本人）、以及下一步建议（等待评审 / 需要补充什么信息 / 与哪条既有反馈重复）。

## 3. 查询与解释进度

### 3.1 定位反馈单

- 用户给了数字 ID → `get_feedbacks_feedbackID`。
- 用户描述产品或标题 → `get_products_productID_feedbacks` 分页拉取后客户端匹配，把候选列给用户确认。

### 3.2 读事实

从详情里取：`status`、`assignedTo`、`processedBy`、`processedDate`、`reviewedBy`、`reviewedDate`、`result`、`solution`、`faq`、`repeatFeedback`，以及 `actions[]`（`action` / `actor` / `comment` / `date`）与其中的 `history[]`（字段级差异）。

`actions[]` 与 `actions[].history[]` 运行时才返回，工具的 Schema 里没有声明——按运行时数据读。

### 3.3 三段式解释

输出分三段，不混写：

1. **事实**：直接来自字段与 `actions[]` 的陈述（谁、何时、把什么改成了什么）。
2. **推断**：基于事实的判断，每条标注「推断」。
3. **无法确定**：接口里没有的信息（如未排期原因）。

例：`plan` 与 `version` 均为空，只能说明「禅道里没有排期记录」，不能等同于「产品经理拒绝了需求」——后者是推断，且必须写明它只是推断。

### 3.4 输出格式

当前状态 / 负责人 / 处理时间线（`actions` 倒序）/ 结论 / 需要补充的信息。

## 4. 补充反馈

补充说明走「更新描述」这条可靠路径：读取原文 → 生成追加草稿 → 用户确认 → 更新 → 回读。

1. **读原文**：`get_feedbacks_feedbackID` 取当前 `desc`。
2. **生成追加草稿**：原文完整保留，下方追加分隔行与追加段落（复现步骤 / 业务场景 / 预期结果 / 实际结果 / 其他说明），标注追加时间与「用户口述，AI 整理」。
3. **用户确认**：展示完整的新描述（原文 + 追加段）。
4. **更新**：`put_feedbacks_feedbackID`，`payload` 里带 `product`（数字 ID）、`title`（沿用原值，禅道要求）与新的 `desc`。`product` 传字符串会被服务端静默忽略。
5. **回读**：核对 `desc` 含追加段，且 `actions` 新增 `edited`。

禅道没有「只评论不改状态」的接口。关闭、激活、解决等流转会改变单据状态，因此不适合承载补充说明。

## 硬约束

1. **写入前确认**：所有业务写入都要用户明确确认后执行。
2. **写入后回读**：按 ID 重新读取并核对内容，「保存成功」的文本不作为落库证据。
3. **不确定先查**：超时、连接中断、返回与预期不符时，先查询核实再决定下一步；同一份内容不重复创建。禅道创建无幂等，盲目重试会造重复单。
4. **身份**：所有操作都以**当前登录账号**（用户本人的禅道账号）进行，禅道里的反馈单留痕在该账号名下。说「这是你提交的反馈」是准确的；不要说成别人的单据。`openedbyme` 指的就是当前登录账号本人。
5. **凭据**：账号、密码、令牌由用户自己在本机写入接入凭据文件；**不在对话里索要、不在回复里回显、不写进任何仓库文件**。地址同理：只从 `config.local.json` 读，不回显。
6. **权限边界**：当前账号看不到的产品与反馈就是看不到。不要绕过禅道权限去达成写入目的；用户看不到时如实说明并指出该找谁开权限。
7. **附件**：MCP 的附件上传实测不可用。用户要传截图时，说明当前能力不支持，请其贴文字说明或走禅道 Web 端上传后再补充描述。
8. **不做人的决定**：关闭、删除、解决、重新打开单据，以及指派负责人，都由人来做；Agent 只提交内容与读取状态。
9. **不写凭据**：账号、密码、令牌、内网地址不进回复、不进代码、不进文档、不进提交记录。
