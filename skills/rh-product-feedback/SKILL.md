# rh-product-feedback

把用户的自然语言反馈变成禅道里的**反馈单**（`feedback` 对象），并支持查询、进度解释与补充说明。

禅道 MCP 的工具名、参数包装、字段与枚举都以实测为准 → 读 [references/zentao-mcp.md](references/zentao-mcp.md)。
本文件只保留流程与硬约束；模板、话术与错误处理按需下钻。

## 术语

- **反馈单**：禅道 `feedback` 对象（`post_feedbacks` 创建、`get_feedbacks_feedbackID` 读取）。
- **草稿**：写库前展示给用户确认的结构化内容。
- **回读**：写入后用返回的 ID 重新读取，核对内容与操作流水。
- **当前登录账号**：本会话登录禅道用的那个账号，就是对话里的用户本人；禅道里的反馈单留痕在它名下。
- **接入凭据**：当前登录账号的账号名与密码（或令牌），存在用户自己机器的凭据文件里，由用户本人写入；会话登录时会被读取，密码或令牌会进入 Agent 上下文。
- **可见范围**：当前登录账号在禅道里能看到的产品的集合；反馈只能落在这里面，查重也只覆盖这里面。
- **自我安装**：agent 读技能包里的地址配置，按宿主把禅道 MCP 登记进去，再由用户自己写入凭据。

## 0. 会话第一步：环境自检与引导

### 0.1 检测禅道工具是否可用

先确认宿主里存在禅道 MCP 的工具（工具名带 `zentao` 前缀，或至少存在 `post_users_login` 与 `get_products`）。

- **可用** → 继续 0.3。
- **不可用** → 走 0.2 引导安装。**不要**向用户索要禅道地址、IP、端口或账号密码。

**不论工具是否可用，都要核对一次地址**（内网地址换过、装错包时，只有这一步能发现）：

1. 读宿主配置里 `zentao` 条目的 url（Claude Code：`~/.claude.json` 的 `mcpServers.zentao.url`；pi：`~/.pi/agent/mcp.json`）。
2. 读技能包内 `config.local.json` 的 `mcpUrl`。
3. 两者不一致（一边为空、或 url 不同）→ **以技能包里的 `config.local.json` 为准**，按 0.2 第 2 条更新宿主配置里该条目的 url（只改 url，保留其他字段），写回前备份，并告诉用户「配置里的地址和技能包里的地址不一致，已更新，重开一次宿主生效」。
4. 两者一致 → 什么都不用做。
5. **不要为了让两边一致去改技能包里的 `config.local.json`**——那是分发下来的文件，用户没同意不要动（见硬约束 12）。

### 0.2 引导安装（自我安装）

按 [references/setup.md](references/setup.md) 执行，要点：

1. 从技能包内的 `config.local.json` 读 `mcpUrl`（内网地址写死在这个文件里，**不回显给用户**）。
   - 文件不存在 → 包不完整（版本太老或复制不全）：让用户重新安装技能包，或直接用禅道 Web 端提交。
2. 按宿主登记 MCP server。**只改宿主配置里的 `zentao` 这一个键**：已存在就只更新地址，保留该条目上的其他字段与别的 server；写回前先备份，写回后复核条目在不在。
   - **先核对地址**：宿主里已有 `zentao` 条目时，把它的 url 与 `config.local.json` 的 `mcpUrl` 比一下。不一致（内网地址换过、装错包）就更新这个条目的 url（只改 url）并让用户重开宿主；一致才跳过登记。
   - Claude Code（主宿主）：用户级 `~/.claude.json` 的 `mcpServers`；改完需要重开宿主。
   - pi（次宿主）：用户级 `~/.pi/agent/mcp.json`；改完执行 `/reload`。
   - 宿主不让改配置、或条目被宿主回写覆盖 → 让用户自己跑 `setup.md` 里的 `connect.sh` / `connect.ps1`，地址由脚本从 `config.local.json` 读，不进对话。
3. 告诉用户需要在本机写入**自己的**禅道凭据，给出 `setup.md` 里的凭据写入命令，让用户自己执行；**不要在对话里索要或回显密码**。
4. 提示用户重开（或重连）宿主让新 server 生效；重开后**先复核 `zentao` 条目还在不在**，不在就重写一次，仍然不行就走第 2 条的降级路径。

安装过程只做这些；不要替用户编造地址，不要把凭据写进任何仓库文件。

### 0.3 认证（需要禅道数据时才做）

调用 `post_users_login`，参数包在 `payload` 内：`{"payload": {"account": "<账号>", "password": "<密码或令牌>"}}`。

- **懒触发**：只在真要读写禅道数据时才登录（提反馈、查反馈，或用户明确说「连上禅道」）；无关问题不登录。
- 只用 MCP 工具登录，**不要用 curl 或直连 HTTP 去调试登录接口**——那会把会话 token 打进终端日志。
- 凭据从**本机接入凭据文件**读（位置见 `references/setup.md`）；不要在回复、日志、代码或文档里回显账号、密码、令牌。
- 凭据文件不存在 → 给出写入凭据的命令让用户自己执行，等用户确认已写入后再登录；**不在对话里问密码**。
- 收到 HTTP 401 → 重新登录一次，重试该调用一次；仍失败则停止并报告认证失败（连续失败可能触发禅道账号锁定，不要反复试）。
- 登录成功后会话内沿用该账号的 token，后续调用自动带 token。会话登录下令牌会进入本次会话上下文，这是已知的暴露面——不要说成「Agent 看不到令牌」。
- **实测提醒**：当前禅道 MCP 的 `post_users_login` 不校验传入的凭据，恒以服务端配置的身份返回成功（详见 `references/zentao-mcp.md`）。所以「登录失败」这一分支目前基本触发不了；一旦 MCP 改为按用户凭据登录，下面 401 的处理规则照旧。

完成标准：拿到一次成功登录；或给出明确的认证失败结论与建议动作。

### 0.4 只读自检

认证成功后调一次 `get_products`（只读）确认真的连上了，并用它列出**当前账号可见的产品**——这批产品就是后续选产品的候选范围。失败则按 [references/error-handling.md](references/error-handling.md) 处理。

自检通过就**直接进入用户的诉求**（收集要素、查重、草稿），不要在中间插入「自检报告 → 等用户确认」的往返；只在认证失败、产品不可见时停下来给下一步。

## 1. 路由意图

| 用户表达 | 流程 | 反馈类型 |
| --- | --- | --- |
| 「帮我装 / 配置 / 连接禅道」「禅道连不上」 | [引导安装](#02-引导安装自我安装) | — |
| 「有个问题 / 页面报错 / 复现步骤是…」 | [提交反馈](#2-提交反馈) | Bug |
| 「需要一个功能 / 希望支持…」 | 提交反馈 | 需求 |
| 「体验不好 / 建议优化…」 | 提交反馈 | 建议 |
| 「反馈 123 什么状态 / 谁在处理 / 处理到哪了 / 为什么还没排期」 | [查询与解释进度](#3-查询与解释进度) | — |
| 「再补充一点 / 又复现了一次 / 补上业务场景」 | [补充反馈](#4-补充反馈) | — |

意图不明时问一句再动手。用户明确要「提交」时，走提交流程；只描述问题但没说要提交时，先确认意图。

**歧义判据**：用户说的是**产品/系统使用中的不便或期望**（“每次查询都要重选筛选条件”）→ 当成给产品的建议，走提交流程（类型 `advice`）；用户明确要改**这个技能本身**（“给这个工具加个记忆功能”）→ 那不是产品反馈，不要在对话里改技能包文件（见硬约束 12），建议他到仓库提 issue。

## 2. 提交反馈

### 2.1 收集要素

按 [references/feedback-templates.md](references/feedback-templates.md) 的模板收集。

- 必备：标题（一句话说清问题）、所属产品、类型、现象或期望、业务场景。
- Bug 追加：复现步骤、实际结果、预期结果。
- 需求追加：期望能力、使用场景。
- 建议追加：现状痛点、期望改进。
- 只追问真正影响分类、复现或验收的信息，一次问全；用户没说的版本号、模块、负责人一律不补写，缺什么就在草稿里写「用户未提供」。

**所属产品**只能从 0.4 列出的**当前账号可见产品**里选。用户说的产品不在其中时，如实说明「你的账号看不到 <产品>，这条反馈暂时无法提交到该产品，请找管理员开权限或换一个产品」，不要报「产品不存在」。

完成标准：模板里每一项都有内容或明确标注缺失。

### 2.2 生成草稿

按模板渲染描述正文。草稿要能独立读懂——用户只看草稿就知道禅道里会存下什么。

### 2.3 查重

禅道 MCP 没有服务端关键词检索，查重靠客户端匹配：

1. `get_products_productID_feedbacks`，`recPerPage=100`，最多取 3 页（上限 300 条）。
2. 在客户端按标题关键词匹配（大小写与空格归一化，取标题中最有区分度的词）。
3. 把候选连同 ID、标题、状态列给用户，让用户选：新建 / 复用候选 / 都不是。

这次扫描同时是本次写入的**基线**：结果不确定时，只有基线里没有的 ID 才可能是本次新建。

只覆盖拉取到的范围。向用户说明「**在你可见的 N 条**中未发现重复」，而不是「没有重复」——可见范围由当前账号的禅道权限决定。

### 2.4 用户确认

展示：类型、所属产品、标题、描述全文、查重结果。

用户明确确认后才写入。只有「嗯」「行吧」而没看到草稿时，先把草稿给出来再问一次。

### 2.5 创建

`post_feedbacks`，全部字段放进 `payload`：

```json
{"payload": {"product": 42, "title": "<标题>", "desc": "<描述全文>", "type": "bug"}}
```

- `type` 映射：Bug → `bug`，需求 → `story`，建议 → `advice`。
- `product` 是产品 ID（整数，示例里的 42 是占位），先从 `get_products` 确认；`product` 与 `title` 是禅道实际必填项。
- `desc` / `source` / `module` / `feedbackBy` 保持不填：反馈者由禅道按当前登录账号自动记录，填了反而与实际留痕矛盾。
- 只发一次调用。创建接口没有幂等键，同一份 payload 发两次会产生两条记录。

### 2.6 回读校验

用返回的 `id` 调 `get_feedbacks_feedbackID`，核对**产品、标题、完整描述**（换行归一化后逐字比较），并确认 `actions` 里有 `opened`。

- 一致 → 进入 2.7。
- 不一致或读不到 → 按 [references/error-handling.md](references/error-handling.md) 处理：先查后报，不重复创建。

**结果不确定时（超时、断连、返回无法解析）**：不重发创建请求。重新扫描该产品，只把「基线里没有的 ID + 回读后产品、标题、完整描述都一致 + 有 `opened` 流水」的候选当作可能的新建：恰好一条 → 按创建成功交付，并说明是查询核实到的；多条 → 报无法唯一确认并列出候选；零条或扫描不完整 → 报未确认，交回用户。

**响应里没有可解析的业务状态**（HTTP 200 但正文为空、或只回了 JSON-RPC 错误）时，按结果不确定处理。参数错误（JSON-RPC `-32602`，payload 缺必填字段）除外：请求根本没被执行，按失败处理并把服务端的原因告诉用户。

### 2.7 交付

给出反馈 ID、标题、当前状态、负责人（没有则说明尚未指派）、提交人（当前登录账号本人）、以及下一步建议（等待评审 / 需要补充什么信息 / 与哪条既有反馈重复）。

## 3. 查询与解释进度

### 3.1 定位反馈单

- 用户给了数字 ID → `get_feedbacks_feedbackID`。
- 用户描述产品或标题 → `get_products_productID_feedbacks` 分页拉取后客户端匹配，把候选列给用户确认。

### 3.2 读事实

从详情里取：`status`、`assignedTo`、`processedBy`、`processedDate`、`reviewedBy`、`reviewedDate`、`result`、`solution`、`faq`、`repeatFeedback`，以及 `actions[]`（`action` / `actor` / `comment` / `date`）与其中的 `history[]`（字段级差异）。

`actions[]` 与 `actions[].history[]` 运行时才返回，工具的 Schema 里没有声明——按运行时数据读。

### 3.3 三段式解释

输出分三段，不混写：

1. **事实**：直接来自字段与 `actions[]` 的陈述（谁、何时、把什么改成了什么）。
2. **推断**：基于事实的判断，每条标注「推断」。
3. **无法确定**：接口里没有的信息（如未排期原因）。

例：`plan` 与 `version` 均为空，只能说明「禅道里没有排期记录」，不能等同于「产品经理拒绝了需求」——后者是推断，且必须写明它只是推断。

### 3.4 输出格式

当前状态 / 负责人 / 处理时间线（`actions` 倒序）/ 结论 / 需要补充的信息。

## 4. 补充反馈

补充说明走「更新描述」这条可靠路径：读取原文 → 生成追加草稿 → 用户确认 → 写前复核 → 更新 → 回读。

1. **读原文**：`get_feedbacks_feedbackID` 取当前 `desc`。
2. **生成追加草稿**：原文完整保留，下方追加分隔行与追加段落（复现步骤 / 业务场景 / 预期结果 / 实际结果 / 其他说明），标注追加时间与「用户口述，AI 整理」。
3. **用户确认**：展示完整的新描述（原文 + 追加段）。
4. **写前复核**：确认之后、写入之前再读一次同一条反馈，核对产品、标题、原始 `desc` 是否仍与生成草稿时一致。被别人改过 → 停止写入，把当前原文与重新合并后的草稿交给用户确认，不自己合并后继续写。
5. **更新**：`put_feedbacks_feedbackID`，`payload` 里带 `product`（数字 ID）、`title`（沿用原值，禅道要求）与新的 `desc`。`product` 传字符串会被服务端静默忽略。只发一次更新请求。
6. **回读**：回读的 `desc` 与**完整预期描述**归一化换行后逐字比较（不是看包含某几段），并确认 `actions` 这次**新增**了 `edited`——历史上存在过 `edited` 不算证据。
7. **结果不明**：更新超时或返回无法解析时只读核实，不重放更新；核实不了就报未确认，交回用户。

禅道没有「只评论不改状态」的接口。关闭、激活、解决等流转会改变单据状态，因此不适合承载补充说明。

## 硬约束

1. **写入前确认**：所有业务写入都要用户明确确认后执行。
2. **写入后回读**：按 ID 重新读取并核对内容，「保存成功」的文本不作为落库证据；补充说明还要确认本次**新增**了 `edited` 流水。
3. **不确定先查**：超时、连接中断、返回与预期不符时，先查询核实再决定下一步；同一份内容不重复创建。禅道创建无幂等，盲目重试会造重复单。写入前保留已扫描反馈的 ID 基线，结果不确定时只认「基线之外、唯一、回读完全一致」的新记录；认不准或复查不完整就报未确认交回用户，不把「没查到」说成「没创建」。
4. **身份**：所有操作都以**当前登录账号**（用户本人的禅道账号）进行。说「这是你提交的反馈」只在回读确认提交人是当前登录账号时才能说；提交人不是本人时（如实说「禅道里这条反馈的提交人是 <另一个人>」），不要把服务端的提交人当成用户本人。`openedbyme` 指的是当前登录账号本人提交的记录。
   - 写完回读时核对反馈的 `feedbackBy` 是不是当前登录账号；不是就如实告诉用户「禅道里这条反馈的提交人是 <另一个人>」，不要把服务端的提交人当成用户本人。
5. **凭据**：账号、密码、令牌由用户自己在本机写入接入凭据文件；**不在对话里索要、不在回复里回显、不写进任何仓库文件**。地址同理：只从 `config.local.json` 读，**不在回复里写出地址的具体值**——汇报连接状态时说「已登记、已连接」即可，不要把 URL 贴给用户。
6. **权限边界**：当前账号看不到的产品与反馈就是看不到。不要绕过禅道权限去达成写入目的；用户看不到时如实说明并指出该找谁开权限。
7. **附件**：MCP 的附件上传实测不可用。用户要传截图时，说明当前能力不支持，请其贴文字说明或走禅道 Web 端上传后再补充描述。
8. **不做人的决定**：关闭、删除、解决、重新打开单据，以及指派负责人，都由人来做；Agent 只提交内容与读取状态。
9. **不写凭据**：账号、密码、令牌不进回复、不进代码、不进文档、不进提交记录。禅道地址随技能包进版本库（ADR-0005），可以读取，但不要主动回显地址的具体值。
10. **并发边界**：禅道更新接口无条件覆盖，没有版本号 CAS。写前二次回读能显著降低覆盖他人内容的风险，但复核与写入之间仍可能有别人改过——发现原文变了就停手，把重新合并后的草稿交回用户确认。
11. **不覆盖宿主配置**：登记禅道 MCP 时只动宿主配置里的 `zentao` 条目，保留别的 server 与该条目上的其他字段；写回前先备份，改完复核条目还在不在。
12. **不改技能包自身的文件**：未经用户明确要求修改技能，不动 `SKILL.md`、`references/`、`scripts/`、`config.local.json` 里的任何文件。用户把“希望这里能记住上次的筛选条件”这类话说成对产品的期望时，按**给产品的建议**处理（类型 `advice`），不是给技能加功能；真要改技能，请他到仓库提 issue。
