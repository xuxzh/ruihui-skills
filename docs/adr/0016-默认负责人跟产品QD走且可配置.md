# 默认负责人跟产品 QD 走，配置可改

建缺陷单时若不写负责人，单子会落到**产品的 QD**（质量负责人）名下——实测：MOMV2.0 的 QD 是 `majiawei`，不传 `assignedTo` 建出来的缺陷单直接挂在他名下；QD 为空的产品则不指派。这条默认出在**接入层**（禅道 MCP 服务端）：同一账号直连禅道 REST v1（`POST /api.php/v1/bugs`）建同一个产品的单子，`assignedTo` 是空的（实测）。

一度把它当成缺陷处理：线上缺陷 #1944 指派给了一个已离职的账号，业务用户既不知道单子被指派给谁，也不知道禅道有这么一条默认。查下来根因不在技能，而在**禅道里的产品 QD 指向了离职账号**——把产品 QD 换成在职的人，现象就消失了。于是定的是：**缺省跟产品 QD 走，但承接人必须看得见**。

「默认负责人」因此做成一个设置（随包 `config.local.json` 的 `bugAssignee` + 本机 `~/.config/rh-zentao/preferences.json` 的 `bugAssignee`），解析顺序 **终端用户明说 > 本机默认 > 随包默认 > 缺省（产品 QD）**，取值 `""`（不指派）/ `"qd"`（产品 QD）/ 账号名。写入脚本在 `bug-create` 时解析并补字段；草稿与交付都写出承接人是谁。

## 考虑过的选项

- **缺省不指派**（一度采用）：单子不落到任何人名下，等人认领。但真正的毛病（QD 指向离职账号）并没有被解决——照旧会把单子挂到那个账号上，只是从隐式变成显式。撤回。
- **只改文档不改代码**（让 Agent 每次显式带 `assignedTo: ""`）：只改一处，但「每次都记得带」是约定不是保证——漏一次，接入层就把单子挂到 QD 名下。
- **写死成「永远不指派」**：符合单次诉求，但公司若要沿用「缺陷先到质量负责人」的流程就没有开关。
- **做成可配置项、缺省跟产品 QD 走**（采用）：把接入层的隐式默认变成显式设置，缺省与禅道既有流程一致，要改有个开关。
- **在草稿前查一次 QD 账号状态**：禅道只有 `deleted` / `locked` 是硬失效标记，**离职查不出来**（账号还在，只是没人登录；用「多久没登录」判定会误报）。所以只挡硬失效，靠草稿具名让人看得见。
- **随包默认与本机默认分层**（采用）：公司可在 `config.local.json` 预置 `bugAssignee`，个人在偏好文件里改；本机优先。

## 后果

- **`config.local.json` 多了一个字段** `bugAssignee`：技能对它是只读的（硬约束 8），只有管理员在仓库里改、随包分发。
- **本机偏好文件多了一个键**：与 `defaultProduct` 同文件，Agent 写设置时合并写，别覆盖已有键。
- **写入脚本多了一点业务判断**：`bug-create` 时按上面的顺序解析并补 `assignedTo`；反馈单没有这个字段，不受影响。
- **Agent 不再自己决定负责人**：它只在终端用户明说时写 `assignedTo`，其余交给脚本与配置——硬约束 1 的措辞随之变成「不改变禅道的分配结果」。
- **`post_bugs` 的 Schema 里没有 `assignedTo`**：但服务端照收（实测），所以这个开关依赖的是未文档化行为——回读要核对 `assignedTo` 是否与生效值一致。
- **mock 要复刻真实行为**：mock 的 `post_bugs` 按产品 QD 自动指派，并在自动指派时记下指派时间与一条 `assigned` 流水；回归测试锁住缺省行为与各配置取值。
- **查询器多了一个 `qd` 子命令**：给出产品 QD 的账号、姓名与账号状态，让承接人在草稿里具名。
