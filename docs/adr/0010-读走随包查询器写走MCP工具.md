# 读走随包查询器，写走 MCP 工具

> 本文记的是迁移前的通道分工：**读走随包查询器、写走宿主里的禅道 MCP 工具**，已被 [ADR-0017](0017-用官方禅道CLI替换自研接入通道.md) 取代——现在读、写、传图都走官方禅道 CLI，随包查询器与写入脚本已下线。本文保留当时的取舍过程。

禅道的列表类接口单次返回几十 KB 到上百 KB 的 JSON（18 个产品 = 25KB，每个产品对象带 70 多个统计字段；29 个项目 = 87KB）。这类响应直接进 Agent 上下文会被截断，Agent 只能反复调小 `recPerPage` 试错、再落盘解析——实测一次提缺陷单耗时 11 分 35 秒，其中约 8 分钟耗在这条路上，而禅道 API 本身只占约 2 分钟。

因此把「读」从 MCP 工具调用里拆出来，做成随包的只读脚本 **查询器**（`scripts/zentao-query.mjs`）：它在进程内调用禅道 MCP、取数、过滤、投影，只把十几行表格打印出来。**写**（建单、更新、流转）仍然走 MCP 工具——写入要保留「用户确认 → 一次调用 → 回读校验」的链路，而这类调用的响应本来就小。

## 考虑过的选项

- **让 Agent 继续直调列表接口**：靠调小分页把响应压到截断线以下。可行但每次会话都要试错（降档试错、并发翻页、落盘解析），且中文标题语序与口语不同，整串包含匹配还会漏检。
- **在宿主里用 codemode 之类的沙箱调用 MCP 再过滤**：pi 上可行，但 Claude Code 没有这个能力，技能要跨宿主就得写两套。
- **让禅道 MCP 支持字段投影**（上游改进[#10](https://github.com/xuxzh/ruihui-skills/issues/10)）：最干净，但要等服务端改；在服务端改好之前，客户端仍然要面对大响应。
- **随包查询器，读写分流**（采用）：客户端自己解决投影问题，任何宿主都能用；写路径原样保留，风险不扩散。

## 后果

- **读不再进上下文**：产品、项目、缺陷/反馈列表、单据详情都由查询器取，原始 JSON 只在脚本进程内存在。查询器的输出是制表符表格，Agent 要的东西（ID、标题、状态、负责人、正文、流水）都在里面。
- **凭据暴露面反而更小**：查询器自己读本机凭据文件并登录，密码与令牌不进 Agent 上下文。会话登录（写路径）仍然是令牌进上下文，两者并存。
- **写路径没有变**：建单、更新、流转仍走 MCP 工具，仍要用户确认、只发一次、回读校验。
- **多了一个 Node.js 依赖**：查询器用 Node 18+ 的 `fetch`。没有 node 的环境退回 MCP 工具分小页取，只抄需要的字段。
- **筛选在客户端做**：禅道 MCP 忽略 `get_products` 的 `name` 与 `get_projects` 的 `status` 参数，也不按 `productID` 过滤项目；分页参数必须是字符串（直连 HTTP 时传数字会被 `-32602` 拒掉）；`id` 的类型在产品（数字）与项目、缺陷详情（字符串）之间不一致。这些实测结论写进 `zentao-mcp.md`，查询器按它们实现。
- **中文关键词匹配用二元组**：用户说「切换语言功能失效」、标题写「语言切换功能失效」是常态，整串包含匹配会漏；查询器把中文切成二元组、英文按词，算「查询词被标题覆盖的比例」。
- **选项目规则改了**：项目列表不按产品过滤，所以优先级变成「与产品同名的项目 → 唯一 doing 项目 → 不挂并注明」，而不是原先的「产品下唯一 doing 项目」。
