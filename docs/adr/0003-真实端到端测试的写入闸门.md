# 真实端到端测试默认只读，写入要过三道闸门
真实禅道 MCP 的端到端测试默认只读；要跑写入闭环，必须同时满足三项环境条件（显式开关、目标产品、允许写入的产品白名单），并在写入前通过前置自检（认证成功、目标产品存在且在白名单内、反馈读取成功）。测试数据带唯一标识，清理只处理本次创建且标识明确匹配的记录，删除后按 ID 复核记录确已消失；创建结果不确定时不重发写入，先查询核实并把残留风险交回人。公开仓库只记录策略，不写具体产品 ID 与名称——授权与目标留在内部渠道，结论同步到 Issue。
## 考虑过的选项
- **一次授权、长期可写**（默认允许在配置好的产品里写入）：省事，但禅道创建接口没有幂等键、服务端不去重，闸门一旦配错就会造重复单或删错记录，且没人知道发生过。
- **只跑 mock、永远不碰真实禅道**（采用前的默认）：最安全，但真实服务端的响应形状、权限边界与删除语义无法被验证——事实上正是这类缺口让「请求被服务端拒绝」一度被误判成「结果不确定」。
- **三道闸门 + 前置自检 + 唯一标识 + 按 ID 复核**（采用）：把一次写入的爆炸半径压到「一条带标识、随即删除且可核验」的记录，换来真实链路的可验证性。
## 后果
- 写入是一次性、逐次授权的动作，不进 CI，也不做定时任务：真实端到端测试需要内网禅道环境与明确授权。
- 前置自检任一项不通过就中止，不写入；声明了写入意图却不满足条件时，整体判定为不通过，而不是「跳过写入算通过」。
- 残留风险由人兜底：删除语义异常时，脚本会报出残留并以非零退出码结束，清理责任仍在人。
- 真实产品可见范围随账号权限变化，「某产品当前没有反馈」这类事实只反映当前账号的可见范围。
