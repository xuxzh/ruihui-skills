# 用官方禅道 CLI 替换自研接入通道

技能接禅道原本是自研拼装：读走随包查询器（[ADR-0010](0010-读走随包查询器写走MCP工具.md)），写走随包写入脚本并带当前账号的令牌（[ADR-0015](0015-读写都走随包脚本写入带用户令牌.md)），图片走直连禅道 REST v2（[ADR-0011](0011-图片上传直连禅道RESTv2.md)）。三支脚本加一个团队自研的禅道 MCP 服务，留下四个未修的服务端 issue（#7/#12 身份、#8 上传、#10 投影）。

禅道官方出了 `zentao-cli`（MIT，npm 包）。一次性验证结论：它在这台 max 8.2 实例上覆盖了技能需要的全部能力——`feedback` 资源可用、所需动作的最低版本都是 max8.0、字段与枚举和现有载荷一一对应、图片能挂到缺陷单与反馈单上（[issue #13](https://github.com/xuxzh/ruihui-skills/issues/13)）。

因此把官方 CLI 作为**唯一**接入通道，随包脚本收缩为一个入口脚本（换令牌、注入、载荷构造、回读校验）与一个查重助手（中文关键词变体）。原先「读走查询器、写走 MCP 工具」的分工不再保留。

## 考虑过的选项

- **维持现状**（自研 MCP + 随包脚本）：三支自研脚本与多个 ADR 都要继续维护；身份、上传、投影三个服务端缺口仍各自需要一个绕行。服务端补上「按传入凭据登录」后，写入脚本可以退回直接调宿主工具，但那也只解决身份一项。
- **在现有通道旁边再加一条 CLI 通道**：同一件事有两条路径时，Agent 与业务用户都要判断「哪条为准」，而判断错的代价是留痕错误或重复建单；每多一条通道还多一份参考文档与字段差异说明。不选。
- **用官方远程 MCP（`zentao mcp-server`）**：管理员部署一次、用户零安装，身份按请求里的用户令牌执行。但它禁止上传本地文件（传图要另开一路），且令牌要放进宿主 MCP 配置、过期即 401，续期还要改宿主配置——正是 ADR-0015 当初否掉同款做法的理由。不选。
- **用官方 CLI 替换现有通道**（采用）：一条通道，读写传图都走 `zentao` 命令；令牌模型不变，仍是「凭据文件 → 换当次令牌 → 经环境变量注入」，不进 argv、不进 Agent 上下文、不落盘。

## 后果

- **随包脚本变薄**：查询器、写入脚本、上传脚本的直连实现下线，合成一个入口脚本加一个查重助手。命令、字段、枚举、错误码的说明从「禅道 MCP 的实测坑」换成「禅道 CLI 的命令与错误码」。
- **首次接入多一步少一步**：多一步「装固定版本的禅道 CLI」（npm 全局安装，依赖 node，技能本来就要求 node）；少一步「登记禅道 MCP」。自研禅道 MCP 不再进入技能链路，降级为给人手动查看用。
- **查重仍留在客户端**：禅道 API v2 的 `filters` 在 max 8.2 上被忽略（加 `title like` 与不加返回同样的条数），与 ADR-0010 记的结论一致。官方 CLI 的客户端匹配（多组「或」、组内「且」）能承载中文二元组变体，自研只剩「变体生成」这一小块。
- **字段名不需要映射**：`feedback` 与 `bug` 的建单字段、枚举、影响版本写法，与现有载荷一一对应；图片上传的关联对象参数也与原 REST v2 脚本一致。
- **反馈单的身份字段要改**：这台实例上禅道不会自动记录反馈者字段，留痕主体是创建者字段（[issue #14](https://github.com/xuxzh/ruihui-skills/issues/14)）。因此反馈单的提交人核对改看创建者字段，反馈者字段由技能显式填当前账号。这与换不换 CLI 无关，两条通道都受影响。
- **版本要锁**：官方 CLI 迭代很勤，固定版本、升级由发版流程显式发起，避免已装好的技能随官方发版改变写入行为。
- **服务端该修的仍然要修**：自研禅道 MCP 的登录不校验凭据（#7/#12）影响所有调用方，不是我们换通道就能解决的。

## 实施结果（2026-11-20）

- **通道定案**：官方禅道 CLI 是唯一接入通道，读、写、传图都走它；团队自研的禅道 MCP 降级为**人工只读排查**——技能不登记、不依赖它，随包配置里的 `mcpUrl` 只留作给人手动查看的地址来源。
- **落地提交**：`ef1c132`（回读兼容 CLI 不返回 `actions`）、`b41d154`（预热反馈列表的首次全局请求）、`1f63ce7`（反馈带图更新按 `fileID` 归一化正文）、`ea5c6a6`（第二账号身份对照的凭据模板），随 [PR #26](https://github.com/xuxzh/ruihui-skills/pull/26) 一起评审。
- **#25 仍是服务端缺陷**（[issue #25](https://github.com/xuxzh/ruihui-skills/issues/25)）：同一令牌的**第一次** feedbacks 列表请求会忽略 `productID`、返回全局记录。客户端在 `runListScan` 前发一次 `page 1 / page-size 1` 的预热请求绕过；预热失败仍有兜底（退回只读第 1 页、把这次扫描标成覆盖不完整、按记录的 `product` 字段做归属校验）。**服务端没有修**，客户端只是绕过；多节点或无粘性会话时需重新验证。
- **回读不再依赖 `actions`**：CLI 0.4.4 的 `get` 不返回 `actions`，所以建单回读用 `openedBy` + `openedDate`、更新回读用正文逐字一致；`actions` 存在时仍校验 `opened` / `edited`。
- **反馈带图更新**：服务端会给 `<img>` 补 `onload` 等属性，正文比较只按 `fileID` 归一化图片标签、不比较属性。
- **身份对照结论**：第二账号实测建缺陷单与反馈单，`openedBy` 都是第二账号；反馈单的 `feedbackBy` 由脚本显式填当前账号，提交人一律看 `openedBy`（[issue #14](https://github.com/xuxzh/ruihui-skills/issues/14)）。自研 MCP 那侧：**随包脚本**带用户令牌时身份正确，但**宿主里的禅道 MCP 工具**不带 Bearer，仍留痕在服务端固定身份——「脚本能写」不等于「宿主工具能写」，不要用宿主工具建单。
