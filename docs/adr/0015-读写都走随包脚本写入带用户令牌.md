# 读写都走随包脚本，写入带当前账号的令牌

禅道 MCP 的 `post_users_login` 不校验传入凭据：传真实账号、传不存在的账号、传空账号空密码，都返回 `status: success` 与**同一个**服务端固定身份；它给出的令牌拿去直连禅道也是有效的——那是服务端那个共享账号的真令牌。于是经宿主 MCP 工具提交的单据全部留痕在那个账号名下，审计追不到真实提交人。线上已经出现：他人以自己的账号提的缺陷单 #1944，禅道里的提交人却是服务端配置的账号（[issue #7](https://github.com/xuxzh/ruihui-skills/issues/7)）。

同一轮实测也发现服务端留了另一个口子：**它会用请求头里的禅道令牌去调禅道**。请求头带 `Authorization: Bearer <用户令牌>` 时，它按那个令牌的归属账号对外服务；令牌无效直接 401 `Not allowed`；`Basic` 不支持；不带这个头则用服务端配置的固定身份。这条通道让「每用户独立账号」（[ADR-0001](0001-每用户独立禅道账号.md)）在服务端侧重新成立。

因此把「写」也从宿主 MCP 工具调用里拆出来，做成随包的写入脚本 **写入脚本**（`scripts/zentao-write.mjs`）：脚本用本机凭据直连禅道换一个属于当前账号的令牌，带着 `Authorization: Bearer <令牌>` 访问禅道 MCP，只发一次请求，只把结果 JSON 交给 Agent。查询器同步改成同一条认证路径，于是读到的可见范围、写入的留痕都是当前账号的。本 ADR 取代 [ADR-0010](0010-读走随包查询器写走MCP工具.md) 的「写走 MCP 工具」，与 [ADR-0011](0011-图片上传直连禅道RESTv2.md) 一样属于「服务端能力有缺口时技能侧直连」的例外。

## 考虑过的选项

- **等 MCP 服务端修好登录**（issue #7）：这是终态，但服务是团队自研的独立服务，本仓库改不了。在它修好之前，每一条单据的留痕都是错的——审计失效是持续发生的损害，不能只靠「如实告知用户提交人是别人」来兜。可作为后续优化，但不是当下唯一选项。
- **让用户回禅道 Web 端手工建单**：能保证留痕正确，但把技能的价值砍掉大半，且把「提单」拆成两个系统里的人工流程。不选。
- **写入直连禅道 REST API**（不走 MCP）：也能拿到正确身份，但要自己维护字段映射（`product` vs `productID`、`openedBuild` 的数组 vs 字符串、`product` 传字符串会被服务端静默忽略这类坑），MCP 已经把这些规范化好了；而且禅道侧的能力缺口会继续长（上传就是例子），直连会越写越多。不选。
- **在宿主配置里给 MCP 登记一个带 `Authorization` 头的条目**（令牌放文件，头值用 `!cat` 或 `${ENV}` 展开）：pi 的头值是每次解析时执行命令，Claude Code 展开的是启动时的环境变量——两边的刷新语义不一致，且令牌会过期；过期后宿主里的调用静默 401。不选。
- **写入脚本带着用户令牌调禅道 MCP**（采用）：身份由令牌决定，MCP 仍是唯一的禅道接入点，字段与坑都复用 MCP 的现成行为；代价是写入从「一次工具调用」变成「一次脚本调用」，多一个载荷文件。

## 后果

- **写入不再走宿主 MCP 工具**：技能要求本机有 node；没有 node 时如实告知并给替代路径（禅道 Web 端自提），不退回宿主工具写单据——那正是留痕错误的来源。
- **宿主里登记禅道 MCP 变成可选**：登记的价值是终端用户自己也能在对话里调禅道工具，但那些工具的身份是服务端固定账号，只适合查看，不适合建单与更新。
- **「登录失败」这个分支重新变得有意义**：换令牌时密码错或账号被锁定都会拿到明确错误（HTTP 400），不再恒返回成功；连续失败可能锁号，所以只重试一次就停。
- **交付要核对提交人**：回读 `feedbackBy` / `openedBy`，它应当等于当前账号；不是本人就如实说明，不把服务端的提交人当成用户本人。
- **mock 要按真实行为改**：本地 mock 原先把 `post_users_login` 实现成「传什么账号就登成谁」，正好把真实服务端的偏差盖住了。现在 mock 复刻真实行为（登录不校验凭据、请求头带令牌才按用户身份、无效令牌 401），并新增回归测试锁住「单据留痕在当前账号名下」。
- **上游依赖仍然存在**：MCP 服务端补上「按传入凭据登录」后，写入脚本可以改回直接调宿主工具（issue #7）。届时本 ADR 由新 ADR 取代。
