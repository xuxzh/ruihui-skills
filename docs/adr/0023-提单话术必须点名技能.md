# 提单话术必须点名技能：宿主按 description 路由，不点名就绕开整条流程

宿主启动时只把技能的 `name` 与 `description` 写进系统提示，正文要模型自己决定读不读（pi 的文档写得很直白：「模型可能没加载相关技能，需要强制时用 `/skill:name`」）。实测里，Agent 看到宿主自带的禅道工具更「直接」，没加载技能就自己把单提了上去——查重、写入前确认、写入后回读、提交人核对一步都没走。

因此面向业务用户的提单话术一律带技能名：`docs/quick-start.md` 的示例句与 `README.md` 的两处示例列表统一以「用 rh-product-feedback 技能：」开头，把「走不走技能」从模型的临场判断挪到用户话术里。凡是走禅道的事都带（提单、查进度、补充说明），不按消息类型分叉。

## 决策

1. **话术带技能名**：示例句统一前缀「用 rh-product-feedback 技能：」。自然语言写法跨宿主一致，pi / Claude Code / Codex 都认；斜杠命令各宿主拼法不同，只保留在 quick-start「换一种装法」里已有的一处说明，不进示例句。
2. **不点名不算错**：用户自己调禅道接口建单是合法路径，技能的护栏（查重、写入前确认、写入后回读、提交人核对）只在技能被加载时生效。文档不把「没用技能」写成违规，只在常见问题里留一个自查出口——Agent 没给草稿就直接报了单号，就到禅道删掉重提。
3. **同口径并加断言**：`README.md` 两处示例列表与 quick-start 的示例句必须一起改；`tests/validate-skills.mjs` 逐条断言，防止有人嫌啰嗦改回自然语言。

## 后果

- 业务用户的提单话术多了一段固定前缀，这是本轮唯一改动到用户操作的地方。
- quick-start 的「快速开始」段仍守住 [ADR-0014](0014-速查段自足与硬上限.md) 的 ≤40 行 / ≤5 内容块（实测 35 行 / 4 块）。
- 残留风险（已知并接受）：用户不照抄示例句时，宿主仍按 description 自动路由，Agent 仍可能跳过技能。要收口得改技能 description、给交付话术加可观测信号，或往宿主常驻指令文件写一条规则——这三条都要动随包技能或用户级文件，不在本轮范围。
- README 与 quick-start 从此互相绑定：改一处必须改另一处，断言会挡住漏改。

## 考虑过的选项

- **只靠技能 description 加强触发词**：description 是宿主保证始终在系统提示里的部分，理论上更根本；但它属于随包技能，且仍不能保证模型一定选技能——留作后续。
- **让技能交付时自报家门**（「经 rh-product-feedback 技能建单」）：给「有没有走技能」一个可观测信号，但同样要改随包技能；不选。
- **接入时往宿主常驻指令文件写一条规则**（pi 的 `~/.pi/agent/AGENTS.md`、Claude Code 的 `~/.claude/CLAUDE.md`）：能覆盖「用户随口一说」的场景，但要改用户级文件、须先征求同意；不选。
- **用斜杠命令强制加载**：确实能强制，但 pi 是 `/skill:rh-product-feedback`、Claude Code 是 `/rh-product-feedback`，用户要记两套；不选。
- **只改 quick-start 不改 README**：README 是业务用户看的入口页，同一仓库教两套说法必然对不上；不选。
- **在文档里把直连说成违规**：直连是用户自己的选择，技能无权封杀；文档只讲清差异（直连没有查重与确认），不禁止；不选。
