# 反馈路径与缺陷路径并存：用户明确要 Bug 时直接创建正式缺陷单

> 「状态流转与指派仍由人决定」这条边界已由 [ADR-0024](0024-放开缺陷与反馈生命周期流转并按操作分级护栏.md) 修订：技能现在经入口脚本做受控的可逆流转、改派与字段编辑，物理删除仍不开放。本文保留当时的取舍过程。

技能原本只写禅道反馈单，[GLOSSARY.md](../../GLOSSARY.md) 把「正式单据」定义为「由人评审反馈单后创建」。业务用户要的是缺陷进缺陷模块，于是增加**缺陷单路径**：与反馈路径并存，用户明确说「提 Bug / 报缺陷 / 页面报错 / 复现步骤是…」时直接创建禅道 `bug` 对象，**不自动附带创建一张反馈单**（禅道没有「反馈转缺陷」的关联字段，两张单互不关联，只会造成同一件事两张单）。默认落点因此从反馈单翻到缺陷单。

## 考虑过的选项

- **保持只有反馈单**：不动模型，也就没有缺陷单路径；业务用户的缺陷永远进不了开发流程，需求解决不了。
- **反馈单 + 缺陷单成对创建**（保留"先反馈后转正式单据"的顺序）：留下评审痕迹，但禅道没有关联字段，两张单各自独立、无法互相查重，反馈单会重复堆积。
- **两条路径并存、默认落点为缺陷单**（采用）：缺陷直接落到它该去的地方；代价是默认写入的对象影响面变大（会进入开发流程、可被指派给具体的人），因此缺陷单草稿必须显式声明这一点，作为刹车。
- **拆成独立技能**（如 `rh-product-bug`）：触发语义更干净，但安装、认证、可见范围、查重基线、回读校验这些基建完全相同，拆开等于让业务用户装两次技能包、写两遍凭据。

## 后果

- **「正式单据」的定义变了**（GLOSSARY 已修订）：正式单据不再默认由人创建。新增术语「缺陷单」与「反馈单」区分两类"提 Bug"。
- **缺陷单直接进开发流程**：禅道缺陷可被指派、可流转，所以 Agent 依旧不做状态流转与指派（硬约束 8）；查询与解释进度只读不改。
- **留痕仍不可靠**：禅道 MCP 的登录接口不校验凭据（[#7](https://github.com/xuxzh/ruihui-skills/issues/7)），缺陷单的 `openedBy` 同样是服务端固定账号。缺陷单影响面比反馈单大，因此回读必须核对 `openedBy`，与当前登录账号不一致就如实说明「这条缺陷单的提交人是另一个人」。
- **字段默认值取自线上实测**：缺陷的 `severity`/`pri` 取 3（占线上样本 82%）、`execution` 不挂（99% 的真实缺陷都不挂执行）、`openedBuild` 取 `trunk`、`module` 不设（MCP 也没有这个参数）。真实缺陷 85% 挂在项目下，所以 `project` 在"该产品下只有一个进行中项目"时默认挂上。
- **不做图片**：禅道 MCP 的 `post_files` 只接受文件名、不接受内容，图片无法进正文（[#8](https://github.com/xuxzh/ruihui-skills/issues/8)）。技能话术明确引导用文字描述。
- **只做缺陷单一种**：需求单（`post_stories`，运行时评审人必填）与任务单不在本次范围；术语上按「正式单据」统一建模，将来扩展不改模型。
