# 放开缺陷与反馈生命周期流转并按操作分级护栏

> 本决策拟修订 [ADR-0008](0008-反馈路径与缺陷路径并存.md) 中「状态流转与指派仍由人决定、Agent 只创建与读取」的边界；保留 [ADR-0018](0018-随包默认负责人改为不指派.md) 建单时默认不指派的策略。

`rh-product-feedback` 迁入官方 `zentao-cli`（[ADR-0017](0017-用官方禅道CLI替换自研接入通道.md)）后，底层通道已自带完整状态流转、`autoFill` 字段局部更新与 `--ids` 批量能力，但技能规范（硬约束 1）与入口脚本 `scripts/zentao.mjs` 仍把写能力限制在创建、正文追加与传图。此前加刹车的原因在于防止无权限或共享身份误操作研发单据，而当前已经落实每用户独立禅道账号（[ADR-0001](0001-每用户独立禅道账号.md)），服务端 RBAC 可以按个人账号承接权限隔离。

因此把 `rh-product-feedback` 的范围扩展到 **`bug` 与 `feedback` 在内网实测版本（`max8.2`）可用的完整可逆生命周期与字段编辑**（含单条与 `--ids` 批量），并由 `scripts/zentao.mjs` 承担按操作风险分级的硬护栏；`story` / `task` / `ticket` / `doc` 等其余模块与物理删除仍留在范围之外。

## 决策

1. **能力范围收口在双对象与 `max8.2` 可用动作**：补齐 `bug` 的 `resolve` / `close` / `activate` / 全字段编辑（含 `assignedTo`）与 `feedback` 的 `close` / `activate` / 全字段编辑。`bug confirm`、`feedback create-bug` 等依赖 `max8.5` 的动作因服务端版本门禁（`E2010`）暂不纳入；其余禅道模块未来另立独立技能，复用认证与 harness 底座。
2. **使用方扩展为全角色共用**：业务用户、研发、QA 与产品共用同一技能，单据能否流转或改派由当前个人禅道账号在服务端的权限决定；新建缺陷单仍保持默认不指派（[ADR-0018](0018-随包默认负责人改为不指派.md)）。
3. **两档分级确认规则**：
   - **免二次确认直通执行**（脚本仍做前置与格式硬核对）：单条可逆流转或非正文元数据微调（如改派 `assignedTo`、调 `pri` / `severity` / `project`），且用户在指令中明确给出数字 ID、动作与全部必填业务参数（无 AI 推断、无 `confirmClose`），并经脚本预检状态合法且非冗余重复操作。
   - **强制二次确认**：新建单据、目标 ID 或必填枚举由 AI 搜索推断补全、触发 `confirmClose`、修改或改写正文/标题（含补充说明追加与 CAS 改写）、以及目标数量 ≥ 2 的批量操作。
4. **脚本层格式与状态护栏**：`scripts/zentao.mjs` 暴露显式领域子命令（`bug-resolve` / `bug-close` / `bug-activate` / `feedback-close` / `feedback-activate`，扩展 `bug-update` / `feedback-update`），强制前置校验枚举（如 `bug-resolve` 的 8 项 `resolution`、`feedback-close` 的 3 项 `closedReason`）与日期格式，拦截已处于目标态的重复闭环（如重复关闭已 `closed` 单据），利用 CLI `autoFill` 做局部字段更新，并在正文或标题改写时保留 `expectedBody` / `expectedTitle` CAS 复核；所有写入只发一次并在写后回读核对。
5. **物理删除排除与批量契约**：明确不开放 `bug delete` 与 `feedback delete`。批量（`--ids`）仅开放状态流转与非正文统一字段编辑，单批上限 20 条；批前由 `zentao.mjs` 拉取目标现状清单供确认并过滤不合法状态项，默认串行执行全部合法项（支持 `--fail-fast`），逐条回读后按「成功 / 跳过 / 失败」三栏汇报，失败项不自动重试。
6. **主文档体量约束**：遵循 [ADR-0013](0013-SKILL.md只留主干与护栏.md)，`SKILL.md` 只留操作分级规则、更新后的硬约束与索引，保持正文 ≤220 行，枚举与细则下沉至 `references/`。

## 考虑过的选项

- **单技能全量代理 `zentao-cli` 40+ 模块**：覆盖面广，但会稀释「产品反馈与缺陷」触发精度并撑爆 `SKILL.md` 220 行上限，还与官方随包 `zentao-cli` 技能重叠——不选。
- **仅在提示词里写二次确认与命令规范，脚本只透传 CLI**：改动最小，但历史实测（[ADR-0016](0016-默认负责人跟产品QD走且可配置.md)、[ADR-0023](0023-提单话术必须点名技能.md)）表明模型容易跳过提示词步骤，必须把格式校验、前置状态检查与回读收在脚本进程内——不选。
- **所有流转与编辑一律要求二次确认**：安全但高频单条操作（如已报出 Bug ID 与 `resolution`）体验繁琐，改为按操作确定性与影响面分两档——不选。
- **同步开放 `delete` 与无限批量**：物理删除不可逆，无上限批量在部分失败时缺乏事务回滚且难以人工对账，第一阶段只做单批 ≤20 条的可逆流转与非正文编辑——不选。

## 后果

- **既有文档需要联动更新**：实施时需同步修订 `SKILL.md` 硬约束 1、新增或扩充 `references/` 生命周期说明、扩展 `scripts/zentao.mjs` 与对应测试（含 `tests/validate-skills.mjs` 断言与 `rh-version` 版本号推进）。
- **禅道工作流差异需实测兜底**：对于处于 `active` 状态的 Bug 直接调用 `bug close` 是否被服务端放行取决于实例工作流配置，脚本只在 `status === 'closed'` 时拦截重复关闭，其余交给服务端判定并在失败时引导先走 `resolve` 再 `close`。
- **批量写无服务端事务**：`--ids` 在中途失败时已成功条目保持落库，客户端靠批前过滤、20 条上限与三栏回读报告控制影响面。
