# 主宿主与首次接入链路：Claude Code 主、pi 次，三阶段 ≤4 次交互

> 其中「首次接入 ≤4 次交互」与「凭据写入方式」已被 [ADR-0006](0006-安装脚本与首次接入.md) 取代；「地址随内部分发包发出」已被 [ADR-0005](0005-禅道地址进版本库.md) 取代；「内网版技能包由打包脚本产出」已被 [ADR-0020](0020-发布线只有skills-sh一条.md) 取代——发布线只有 skills.sh 一条，打包脚本已下线。本文保留当时的取舍过程。

业务用户的首次接入（从技能包已在机器上到能提交第一条反馈）定为三个阶段：连接禅道、写入本人凭据、提交第一条反馈；验收口径是用户主动发起的交互不超过 4 次，全程不需要手改配置文件、不需要手填地址。主宿主定为 Claude Code，次宿主定为 pi。凭据路径上，会话登录是 MVP 的唯一路径，令牌会进入 Agent 上下文这一点必须如实写进公开文档，不等禅道 MCP 的请求头令牌支持。内网版技能包由仓库内的打包脚本产出顶层自洽的 `rh-product-feedback/` 目录，用户复制这一个目录即完成安装。

## 考虑过的选项

- **主宿主选 pi**（技术上更顺：`/reload` 改完配置不必重启宿主，`pi mcp add` 行为可预期）：没选。业务用户实际在用哪个宿主，比技术优劣更重要；主宿主选错，Quick Start 就与真实使用场景脱节，整轮验收都失去意义。
- **用宿主 CLI 自行注册 MCP**（`claude mcp add --transport http ... --scope user`）：没选。它拒绝更新同名 server（报 "already exists in user config"，地址变了也不更新），而 pi 的 `pi mcp add` 是整条替换、会静默丢掉 entry 里已有的字段——两者都做不到「已存在同名 MCP 时安全更新、不覆盖其他配置」。改为由 Agent 程序化读 `~/.claude.json`、合并 `mcpServers.zentao` 后写回，用户不手改 JSON。
- **等禅道 MCP 支持 `Authorization: Bearer` 再上线**：没选。客户端侧的接缝已经就位（pi 的 `--bearer-token-env-var`、Claude Code 的 `--header`），缺的只是服务端支持；等它会把接入推迟到禅道 MCP 侧的排期之外。请求头令牌记为 MCP 侧待办。
- **内网包由管理员手工拼装**：没选。地址、目录结构、脚本位置三处都靠手工保证，正是当前文档与分发包断点的来源；改为打包脚本产出。

## 后果

- Claude Code 改完 `~/.claude.json` 需要重开会话才生效，因此「重开宿主」是连接阶段的收尾动作，必须在 Quick Start 里显式写成一步，不能当成隐含动作。
- 凭据的暴露面写进 README 与 setup.md：凭据由用户本机写入，但会话登录下 Agent 需要读取该文件，令牌会进入本次会话上下文——优先用可单独撤销、可设有效期的禅道令牌。
- 主宿主承诺「安装 → 认证 → 自检 → 自然语言提交」闭环；次宿主只承诺基本安装与认证可用。两者的支持程度在文档里分开表述，不宣称全宿主兼容。
- 本轮只做主宿主闭环；次宿主的安装与认证验证、安装诊断用例另开 issue。
- 技能安装位置按宿主区分：Claude Code 是 `~/.claude/skills/`，pi 是 `~/.agents/skills/`——同一个 `rh-product-feedback/` 目录在两处都能用，装错地方宿主就发现不了技能。这修正了 ADR-0002 里「通用技能目录」的措辞。
- 内网版技能包的地址由打包脚本写入 `config.local.json`，不进仓库；公开版仍只有占位地址。
