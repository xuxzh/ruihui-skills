# 图片上传直连禅道 REST v2，MCP 上传通道留作上游依赖

禅道 MCP 的 `post_files` 只有 `fileName` 一个入参，没有内容字段，调用一律返回「文件上传失败，文件格式不在规定范围内」；禅道 v1 API 也没有上传接口。能传内容的是禅道 REST v2 的 `POST /api.php/v2/files`（multipart：`file` + `objectType` + `objectID`，禅道 22.0+）。因此随包的上传脚本 `scripts/zentao-upload.mjs` 直连禅道 REST v2 完成上传，单据正文里放固定形态的图片引用（相对路径 + 文件 ID）。MCP 服务端补上传工具作为上游依赖跟进（[issue #8](https://github.com/xuxzh/ruihui-skills/issues/8)），届时只换调用点。

这与 [ADR-0010](0010-读走随包查询器写走MCP工具.md) 的「写走 MCP 工具」是同一条边界上的例外：读仍然走随包查询器，建单与更新仍然走 MCP 工具，只有「把图片字节交给禅道」这一步走直连 HTTP——它不是一次业务写入，而是把文件交给禅道的存储。

## 考虑过的选项

- **改禅道 MCP，加一个能传内容的上传工具**（调用面最干净）：写入链路只剩 MCP 一条，技能侧不用管凭据与 HTTP。但 MCP 是团队自研的独立服务，本仓库改不了；在服务端改好之前，业务用户仍然提不了带截图的反馈。
- **用 base64 把图片内联进正文**（最省事）：不需要任何上传通道。禅道富文本不认 `data:` 内联，消费端（如 zentao-assistant 桌面端）会把这种标签整条剔除——实测也不成立。
- **让用户去禅道 Web 端手动上传，再补充说明**（不写代码）：可用，但把「贴图 → 成单」拆到两个系统里，业务用户每次都要多走一趟。
- **技能侧直连禅道 REST v2 上传**（采用）：绕过 MCP 的能力缺口，图片当次就能进单据。代价是多一条直连 HTTP 的链路、多一个凭据使用点，且与 ADR-0010 的边界不一致，需要单独说明。

## 后果

- **上传必须挂在已存在的单据上**：禅道要求上传时带单据类型与单据 ID，所以顺序固定为「先建单 → 再传图 → 再更新正文」，正文要走一次更新而不是一次创建。
- **图片引用用相对路径**：不把禅道地址写死进正文（地址随部署变），消费端按自己的禅道地址拼出可访问的链接。
- **上传要有回读证据**：脚本回读文件字节并比对大小，还读禅道的文件元数据确认挂在目标单据上——禅道 v1 的 `files` 字段对反馈单与缺陷单恒为空数组，不能用它判断图片有没有挂上。
- **凭据使用点多了一处**：上传脚本自己读本机凭据文件登录，令牌只在进程内使用、不打印；MCP 登录拿不到可用令牌时改走禅道官方令牌接口。
- **上游依赖仍然存在**：MCP 服务端补上 v2 上传工具后，上传脚本应当改回走 MCP，本 ADR 届时由新 ADR 取代。
